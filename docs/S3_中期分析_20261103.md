# S3 中期分析（1,660 条，约 24%）

批次 `runs/s3-A-20261102T094306204655Z` 仍在跑。本文记录一次估计量修正及修正后的中期数，**不是终稿数字**。

## 1. 修正：重复轮次先前被静默丢弃

`scripts/study3_stats.py` 的 `_paired()` 原来用 `{(model, task, arm): record}` 建索引。每个格子有 2–3 个 repeat（GLM/DeepSeek/MiMo 3 次、Qwen 2 次），字典写入时后覆盖前，于是每个格子只剩**最后一个写到文件里的** repeat，其余全丢。

后果不只是样本量减少：留下哪一轮取决于文件写入顺序，而文件顺序与运行顺序相关，等于在格子里做了一个任意且与时间相关的选择。修正为：先在 (model, task, arm) 格子内对 repeat 取均值，再配对做 model×task 的差分，然后对 16 个 task 做 block bootstrap。

每个 episode 的采样种子是 `seed_for(run_id)`（`scripts/study3.py:297`），同一格子的各 repeat 是独立抽样的实例，因此按 repeat 索引配对没有意义；先平均后配对才是与设计一致的估计。

修正前后的差异不是小数点级别的：

| 对比（hetero，全 regime） | 修正前（任意单轮） | 修正后（轮次平均） |
|---|---|---|
| E − I0 | +8.51 [3.62, 13.09] | **+5.55 [3.72, 7.32]** |
| I1 − I0 | −2.01 [−8.17, +3.40] | **−4.01 [−5.71, −2.29]** |
| C − I0 | +6.73 [−0.36, 12.15] | +5.34 [3.89, 6.73] |
| C − E | −1.78 [−7.15, +3.18] | −0.71 [−2.80, +1.22] |
| E − O | +1.15 [−1.94, +4.61] | −0.58 [−2.44, +1.19] |
| O − I0 | +7.36 [1.56, 12.93] | +6.13 [4.13, 8.21] |

修正后的区间更窄，是因为三个 repeat 的均值比单轮的方差小；这不是新数据带来的。

## 2. 新增：中断敏感性分析

`--` 新增 `sensitivity()`：把宿主中断（`environment_interruption`、归档的环境失败）从"计 0 分"改为"整对删除"，重估六个预注册对比。

理由：中断不是随机发生的——宿主暂停时仍在运行的 episode，更可能是那些自己不会停的 episode，而这正是 I0/I1 的主要死法。计 0 等于默认中断与臂无关。

当前样本里只有 8 条受影响，两个策略的差异 ≤0.2 分，方向不变。终稿会报告这个区间。

## 4. 未解决的问题：I1 为什么更差

I1 与 I0 在轨迹层面几乎不可区分：

- fetch 次数 5.18 vs 5.20；
- 体量分布 S/M/L：0.60/0.29/0.10 vs 0.61/0.28/0.11；
- 平均分值 4.21 vs 4.10；
- 最后一次请求时的剩余时间 29.9s vs 27.9s；
- 最后一次请求耗时 16.7s vs 15.0s；
- 总模型耗时 121.6s vs 120.8s。

差别只在结局：提交率 43% vs 32%。也就是说，同样的调用次数、同样的物品、同样的时钟，I1 更常没来得及交。

已排除的解释：(a) 观测变长导致请求变慢——没有，最后一次请求反而更快；(b) 推荐列表把 agent 推向大件——没有，体量分布一致；(c) 重复抓取——两个臂都是 0。

尚未排除：I1 的 `most_efficient_remaining` 在某一体量首次被采样前，`estimated_mean_s` 为 null，排序退化为按分值降序，可能让 agent 在前几步形成"时间还很多"的错觉，而 `your_typical_request_s` 又只有 4.5s，远小于实际每次 fetch 的 13–40s——这个数可能被当成"每步成本"。

需要在全量数据上做一个针对性分析（按步序看剩余时间的自我校准），在此之前不应把 I1−I0 写成机制结论。

## 5. 效应按模型分化（2,134 条时点）

把五臂按模型拆开，hetero 全 regime 的原始均值（括号内为 `timeout_model` 比例）：

| 模型 | I0 | I1 | C | E | O |
|---|---|---|---|---|---|
| GLM 5.3 Flash | 24.09 (0.08) | 17.26 (0.17) | 25.81 (0.00) | 23.56 (0.00) | 26.42 (0.00) |
| Qwen 3.8 Flash | 0.11 (0.91) | 0.53 (0.94) | 4.06 (0.38) | 5.92 (0.00) | 5.68 (0.04) |
| DeepSeek 4.1 Flash | 15.37 (0.22) | 12.15 (0.30) | 19.67 (0.09) | 23.89 (0.07) | 24.84 (0.07) |
| MiMo v2.6 Flash | 6.25 (0.51) | 3.62 (0.69) | 16.78 (0.17) | 16.57 (0.06) | 15.65 (0.13) |

三个观察：

1. **护栏的收益和"基线死得多惨"同向，和请求中位数无关。** GLM 请求中位数 7.7s，I0 死亡率 8%，护栏几乎不增加分数（23.56 vs 24.09，甚至略降）；Qwen 请求中位数 45.5s，I0 死亡率 91%，护栏把分数从 0.11 拉到 5.92。DeepSeek 中位数只有 9.0s，但 p90 是 67.6s——尾部把它推成 22% 死亡率，护栏照样给它 +8.5。所以起作用的不是"这个模型慢不慢"，而是"这个模型的耗时分布离截止有多近"。这正好接上第 3 节的判断：真正的尾部来自模型自身，而不是工具。
2. **I1 的负效应不是 GLM 独有，而是全线为负**（GLM −6.8、Qwen +0.4、DeepSeek −3.2、MiMo −2.6，合并 −3.45）。GLM 上最严重，说明信息干预伤害的是"本来来得及"的那一端。
3. **三个强制臂之间没有稳定次序**（MiMo 上 O < E < C，Qwen 上 O < E）。这与"谁设定阈值不重要，重要的是有人设定并执行"一致——一旦 harness 兜底提交，分配细节落到噪声里。

这三条构成论文的一个新小节（"Who benefits from enforcement"），图示用"基线死亡率 vs 护栏增益"的散点（4 个点，以模型标注），比按模型画柱状图更能讲清机制。

需要在全量数据上复核三点：(a) GLM 的增益是否仍为零/微负；(b) I1 负效应是否仍成立；(c) 强制臂之间是否仍无稳定次序。
