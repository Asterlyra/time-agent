## 1. 研究到底想得到什么

核心问题是：**在工具耗时发生变化、任务有墙钟截止时，给模型提供基于最近观察的工具耗时摘要，能否帮助它选择更合适的行动，并提高截止前正确完成任务的概率？**

三组共同拥有剩余时间、初始校准样本和历史工具耗时。A 无额外摘要，B 给固定初始均值，C 给近期动态均值。因此本轮研究摘要的增益，不研究“有无时间信息”，也不训练模型。

希望得到四层证据，后一层不能由前一层自动推出：

| 层次 | 要回答的问题 | 应得到的材料 |
|---|---|---|
| 实验可行性 | 任务能解、模型能收到变化反馈，之后还有行动机会吗？ | 完整开发矩阵、可解性/暴露/服务质量检查 |
| 端到端效果 | C 是否改善截止前正确率，相比 B 改善多少？ | 各模型配对结果、等权汇总及不确定区间 |
| 行为机制 | 模型是否改变检索路径、重复查询、计算或提交选择？ | 分阶段动作记录、证据覆盖和代表性配对轨迹 |
| 适用边界 | 哪类任务、模型或预算下有效、无效或有害？ | 分层描述、失败归因、明确不能推广的范围 |

工作假设是快变慢时 B 的参考可能过时，C 可能改善决策；也接受无差异、C 更差、仅部分模型受益等结果。不能把研究目的写成“证明 C 一定获胜”。

### 2.2 更严格的变化经历

本次另外检查：当前 episode 是否对同一种工具，既有变化前的完整观测，又有变化后的完整观测，且之后有下一次模型请求。v5 只有 **4/6** 满足：证据 2/3、表格 2/3。旧口径的 6/6 不等于六次都亲历同类工具的变速；初始校准提供的是额外基线。

这项检查是本次事后新增的描述，不能反过来筛选旧批次做效果比较。后续开发阶段应同时记录宽、严两种暴露口径。

### 2.4 不能怎样使用旧数据

- 不把 v2→v3→v4→v5 的差异解释为某个修改的因果效果；任务协议、预算、调用环境和运行时刻发生了变化。
- v4/v5 绝对变化点同为 36 秒；v5 改成 180 秒且变化比例为 20%，不能说只改了一个参数。
- 不跨批次合并同名 run_id；清单未编码所有版本信息，同名 ID 可能对应不同配置，定位必须包含批次目录。
- 更早两个部分批次分别完成 9/72、正确 5/9 和 7/9；一个批次无标准结果；早期 v3 启动失败批次为 1/18、0 次成功并记 service_error。它们保留作故障证据，不混入完整批次比例。
- 当前全部主要数据来自单一 Luna 模型，不能据此判断 GLM、Qwen、DeepSeek 的表现。

## 3. 后续设计原则：先让实验有解释力，再增加运行数

现有数据呈现两个相反的问题：任务太容易结束时看不到变化；强行增加调用深度后又容易全部超时。所以下一步不能只扩大 v5，也不能按 C 的胜负反复选预算。

开发阶段要同时满足：基本可解、变化反馈可达、反馈后仍有选择空间。任务中应存在不同成本且能满足同一评分要求的合法路径；减少必要证据、提前乱猜不算有效优化。模型请求开销与工具等待必须拆开记录。

候选修改和质量门槛可写入计划，只有实际验证后才能称为已实现。正式测试集只在冻结后执行；本次制定计划不查看正式测试结果。

## 4. Agent 与模型配置建议

### 4.1 固定同一个 Agent

主实验建议保留 Python runner、任务、动作协议与评分，新增薄 API 适配层。三个模型都走同一条实验流程，不给某个模型使用更强的 planner、额外工具或独立框架。

OpenCode 自定义 agent 作为后续框架复现，不与主实验样本混合。当前 CLI 轮次启动/退出和 Windows 隔离问题先作为历史开发限制记录，不能绕过现有正式门禁直接开跑。

### 4.2 三个候选模型

| 家族 | 候选 ID | 处理原则 |
|---|---|---|
| GLM | `glm-5.3-flash` | 检查协议与基本可解性，不预设速度和效果 |
| Qwen | `qwen3.8-flash` | 同上；原生 API 与另外两者不同，适配层需核对 |
| DeepSeek | `deepseek-v4.1-flash` | 同上；核对账户模型和区域权限 |

模型 ID 与接入方式于 2026-10-30 查阅[官方模型目录](https://opencode.ai/v2/docs/console/models)。原生 API 差异由薄适配层处理，共同观察和 JSON 动作语义保持一致。记录精确 ID、可见版本、接口、温度、输出上限、推理模式和缓存用量；不假定跨供应商同名参数代表同等计算量。

可选第四模型 `gpt-6-luna` 用于桥接旧开发观察，但属于另登记的扩展；旧 CLI 结果不能并入新接口结果。模型若因权限、退役或协议不兼容而更换，应在正式前登记原因、重做该模型开发验证，不能因 C 表现不佳换模型。

### 4.3 Go 的可用性与范围

官方支持[其他 coding agent 通过 Go 接入](https://opencode.ai/v2/docs/console/harnesses/)，但[Go 用途说明](https://opencode.ai/v2/docs/console/go/)定位于 coding-agent 请求。当前合成表格/检索批量实验是否覆盖，仍需确认；换用 OpenCode 客户端不会自动确认用途适用性。

Go 适用时使用真实客户端标识和每 episode 稳定会话 ID；不适用时使用允许该研究用途的按量渠道。当前未读取账户余额或做收费探测。实际执行前确定费用上限和剩余额度；服务限额不作为工具延迟操纵。

## 5. 分阶段执行与准入条件

以下数量为计划，不是已运行数据。门槛是新的开发质量标准，不能拿它追溯删除旧数据。正式前将这些规则及任何修订版本登记，开发报告先看池化质量指标，不按 A/B/C 胜负挑配置。

### 阶段 0：不调用收费模型的执行验证

用模拟响应验证：

1. 完整 JSON 动作接收时刻、临界截止与取消；清理耗时另记，迟到提交不计成功。
2. 429/5xx/网络错误分类、最多一次任务内重试、预算不重置。
3. 非法工具、错误参数、格式修复、首次有效提交终止及私有评分不返回模型。
4. 工具边界、凭据持有范围、模型不能读取答案或其他 episode 数据。
5. B 不更新，C 仅使用完整同类工具样本；无跨 episode 状态残留。
6. journal、started 标记、不覆盖式写入、配置变化拒绝恢复与中断记录。

实际模型请求只有宿主适配器能发出；若 API 模型仅生成文本，仍需验证工具执行器和数据装配，不能把“无 CLI”当作已通过隔离检查。模拟通过只能进入真实开发验证。

### 阶段 1：模型协议与基本能力检查，建议 18 次

三个模型 × 两类各一道开发题 × 三次重复 = 18 个 episode；stable_fast、A、诊断预算 300 秒，工具目标仍为 2 秒。独立标签保存，不进入正式比较。

每个模型每类至少 2/3 正确且没有未解决的认证、协议或越权问题，才进入下一阶段。未达标时先区分接口错误、数值错误、证据错误和任务不可解；不能直接归因为时间适应不足。

这 18 次用于筛查接口和基础能力，不足以评估稳定可靠性。完成后登记请求延迟分布、实际 token/费用和可见设置，不用公开模型榜单代替实测。

### 阶段 2：完整开发校准，216 次

矩阵为 `3 模型 × 8 道开发题 × A/B/C × 3 延迟模式 × 1 次 = 216`，每模型 72 次。

第一候选保持 v4 任务接口及 v5 的 `180 秒 / 20% / 2–15 秒 / 窗口 3 / 最多 20 轮`。慢变快按慢阶段预校准，另两种模式按快阶段预校准；不能把 v5 仅有的 fast 校准直接用于慢变快。

建议采用以下开发准入门槛：

| 维度 | 新批次的建议检查规则 | 不通过时做什么 |
|---|---|---|
| 基本可解性 | 每模型×任务族的 stable_fast，池化 A/B/C 至少 6/12 正确 | 查接口、证据规则及机械开销；不得只增加时间到所有题都轻松完成 |
| 宽口径暴露 | 每模型×任务族×变化方向，池化 A/B/C 至少 9/12 有新阶段完整反馈后再发请求 | 检查任务深度与变化点；同时保留提前完成的正确任务 |
| 同类工具两阶段经历 | 逐单元报告有同类工具前后完整观测及后续请求的数量，作为描述指标，不强制至少 6/12 | 初始校准也是共同旧阶段基线；不强迫高效路径重复搜索以满足门槛 |
| 决策空间 | 对已暴露运行，至少 2/3 在首次新阶段结果后获得一个有效动作 | 判断剩余预算是否足够，检查任务是否只有固定机械路径 |
| 主环境难度 | 每模型池化两任务族及 A/B/C 的 fast_to_slow 共 24 次，至少一次成功、一次失败；各单元仍报告饱和情况 | 为预定主问题检查地板/天花板；不要求所有次要单元都必须失败 |
| 记录与服务 | 无未解决的协议/越权问题；若服务异常 episode 超过 5%，暂停并审查整个配置批次 | 排查供应、限额和实现；不能删去故障后当完整批次 |

这些小样本阈值是实务筛查，不能证明统计功效或方法有效。逐条件列出原始数与分母检查明显失衡，但不以 C 的成绩决定是否通过。高 stable_fast 正确率不是单独的淘汰理由；变化环境仍应有成功和失败。

2026-10-30 修订理由：采用 12 秒变化点时，首个 15 秒慢搜索结束前已经变快，一次搜索后读取全文的高效路径可能没有同类工具在 episode 内的双阶段样本。将此作为硬门槛会偏向冗余搜索；保留描述，主要准入仍要求收到变化后完整反馈及后续有效动作。同时，地板/天花板准入聚焦预先指定的 fast_to_slow 主问题，次要模式和任务子单元的全对/全错如实报告，不为制造失败而改任务。这些修改在新完整开发矩阵前登记，不以 C−B 效果选配置。

若需修改，先写明哪个质量门槛失败和对应原因，再建立新候选版本。例如：

- 任务经常在变化前完成：检查信息获取深度、阶段时刻与模型调用速度。
- 看到了变化却几乎都超时：先拆解请求延迟和工具等待，再考虑降低机械成本或调整共同预算。
- 数值对、证据错：核对题面、证据定义和评分；不能为个别失败放宽集合规则。
- 没有合法路径选择：增加可验证的筛选/摘要入口或任务结构，避免只靠强制更多分页制造压力。

每次修改都保留旧版本，并在开发集验证；不能同时扫很多参数再挑 C−B 最大者。API 接入后速度可能明显不同，旧 CLI 的 180 秒和 36 秒只能是候选，不能直接冻结。

当前执行另登记有限自动规则，详见[执行记录](执行记录_20261030.md)：完整开发结束后，最多两轮新矩阵；仅按主环境池化地板/天花板、变化暴露和反馈后动作调整共同预算或绝对变化点。基础正确性不足、模型间方向冲突或服务异常不通过自动增加时间解决。绝不按条件差值选参数，也不无限试到通过。

### 阶段 3：冻结后的主实验，目标 1,080 次

`3 模型 × 20 测试实例（每类 10）× 3 条件 × 3 模式 × 2 次重复 = 1,080`。

基础诊断已采用每模型并发 1、全局最多 3。按用户授权加速，新完整开发批次固定每模型并发 2、全局最多 6，并保持同一 A/B/C 配对块由同一 worker 依清单顺序完成；两个 worker 处理不同块。正式并发必须与通过验证的开发配置相同。配对块共享公开任务、起始校准和延迟规则，动态状态各自独立。

冻结内容包括任务和评分版本、模型设置、接口、完整提示、工具说明、校准方法及样本、预算、变化比例、窗口、重试、清单 seed、并发、费用上限和统计方案。若用户级模型配置或模型服务发生可见变更，暂停记录，不能悄悄把变更前后数据视为同一固定配置。

资源不足时，在查看正式效果前按原方案缩到每类五题，共 540 次，保留三模型、三条件、三模式与两次重复。此时独立任务更少，应定位为探索性结果。

旧正式入口与最新流水线不一致，需要另建或改造并验证；保留当前 fail-closed 保护，不能仅删除阻断判断。

### 阶段 4：固定上下文的机制探针，可选且单独登记

若要更清楚地区分“参考改变动作”和“随机运行轨迹恰好不同”，可从开发集构造八个公开决策前缀，固定题面、已读内容、过去工具耗时和剩余时间，只改变 A/B/C 的摘要字段。

`3 模型 × 8 前缀 × 3 条件 × 2 次重复 = 144 次单步决策采样`，不是 144 个完整任务。C 必须按前缀中的真实已完成耗时计算，B 保持初始均值；示意剩余时间可固定为 60 秒，并明确这是受控输入的探针。

事先按前缀定义允许动作及其解释，例如是否重复查询已知行、是否使用合法筛选路径、证据已充分时是否提交；不能一律把少调用或提前提交标为更好。只测下一步倾向，不能直接推断端到端成功率或真实适应速度。

此扩展入口现已实现为 `scripts/mechanism_probe.py`，当前五个针对性单测通过，真实采样尚未执行。前缀仅从完整通过开发的八道题选择；不为主结果显著性临时增设或替换主比较。

## 6. 主指标、机制指标与统计

### 6.1 主问题与估计量

主指标为 `deadline_success`：截止前完整有效提交，且数值和证据同时正确。主要比较为 fast_to_slow 下 C−B，各模型分别报告，再作固定三模型的等权平均。

主分析包含提前完成、未暴露、超时和错误提交的所有已启动 episode。不能仅挑收到变化反馈的运行比较成功率，因为是否暴露受模型行为影响。既定重试后服务失败保留为端到端失败并单列；协议/隔离问题要求暂停审查，不能自动当普通模型失败解释。

完整清单尚有未启动或未结束项目时，不报告完整计划矩阵的最终效果。按已启动记录的临时结果明确分母；不覆盖式中断记录与敏感性分析并列，不能只用完整配对子集伪装全样本估计。

### 6.2 次要和机制指标

| 指标 | 解释用途 | 不能推出什么 |
|---|---|---|
| C−A、B−A及其他模式结果 | 摘要与动态更新的不同作用 | 不自动等于预注册主比较成立 |
| 数值/证据错误分别统计 | 区分推理、证据管理与时间问题 | 数值正确不等于任务成功 |
| 模型请求、工具等待、循环开销 | 找时间花在哪里，报告分位数与删失 | 请求墙钟不等于纯推理 |
| 暴露及反馈后有效动作 | 检查反馈是否有被使用的机会 | 获得机会不等于理解或利用 |
| 首次变化反馈后的动作序列 | 检查重复查询、合法筛选、证据覆盖与提交 | 工具调用少不必然更高效 |
| C 参考与下一次同类完整耗时的误差 | 诊断统计器更新及滞后 | 不等于模型本身会预测耗时 |
| token、缓存、费用和套餐额度 | 估算资源和复现成本 | 套餐扣费为零不等于不占额度 |

轨迹案例按预先规则选择：覆盖 C/B 成败四种组合，各取排序后的第一对，并补充每类主要错误的实例；不存在的组合明确标注，不只展示有利案例。

### 6.3 不确定性和样本规模

配对单位为任务×模型×模式×重复；bootstrap 按任务实例抽样，保留该任务所有模型和重复，固定 seed，10,000 次重采样，报告 95% 区间。可按两任务族分层抽样，固定其权重；统计脚本是否支持该变体需在冻结前验证。

每模型每条件每模式虽有 40 次运行，独立任务只有 20 个；两次重复不等于 40 个独立任务，模板共享结构还限制推广。这个规模适合估计较明显效应和可行性，不保证检出几个百分点的提升。

以 5 个百分点作为本轮资源投入的实务关注阈值，而非已证明可检测的最小效应。区间跨零时不宣称改善；若区间仍覆盖明显正负收益，结论是证据不足，不能说“无效”。若整个区间位于 ±5 个百分点内，可描述所测设置下大幅收益不被支持，不能据此宣称严格等效。

是否扩大独立任务数，应依据开发期配对波动、资源与预设精度目标，在正式效果分析前决定；不能持续加样直到显著。逐模型显著性检验如需开展，列为探索性或做多重比较校正。

## 7. 想看到的行为，以及相反结果如何解释

| 可能结果 | 可以支持的判断 | 后续处理 |
|---|---|---|
| C−B 为正且区间不跨零，多模型方向一致，行为也减少冗余并保持证据充分 | 所测环境中动态摘要有助于预算内任务完成，轨迹与策略解释相符 | 报告效应及边界，考虑固定上下文/框架复现 |
| C 成功率提高，但行动轨迹未显示清楚差别 | 有端到端增益证据，机制仍不明 | 不宣称已证明策略适应，补机制检查 |
| 动作变了，成功率无明显改善 | 模型会响应摘要，但响应未转化为任务收益 | 查证据错误、预算瓶颈及无收益动作 |
| B/C 都优于 A，C 与 B接近 | 摘要可能有帮助，动态更新的额外收益未建立 | 保留简单固定参考作为实际选项 |
| C 更差或只对一个模型有利 | 存在误导、均值滞后或模型依赖，需证据进一步归因 | 不概括为普遍能力或普遍失败 |
| 大多数任务提前结束或全部超时 | 操纵和任务难度尚不足以回答问题 | 记录开发失败；冻结前修正，不用正式结果反向挑题 |
| 差值小但区间宽 | 样本不足以判断 | 如实报告不确定性，另登记更大独立任务实验 |

最有价值的交付是能说明“有没有用、作用多大、什么时候有用、为什么可能有用”的证据链。负面或不确定结果同样可以界定后续工作，不能被改写成成功。

## 8. 资源、时间与交付

按 180 秒预算，主实验 1,080 次串行预算总和为 54 小时；每模型并发 2、全局最多 6 的理想预算上限约 9 小时，尚不含限额等待、校准、恢复和分析。540 次对应约 4.5 小时。216 次开发按同一预算约 1.8 小时理想并发时间；已完成的 18 次诊断采用全局并发 3。不同阶段及按模型负载不均会影响实际时长，不能保证两天内完成。

用开发集实测的多轮 token、缓存与调用量估算各模型套餐消耗；按五小时、周和月限额分配批次。缺少账户额度及费用上限时，仍可完成文档和离线验证，不能据此自动开始收费扩量。

## 2026-10-31 测量协议修订

本机旧 `time.monotonic()` 在休眠中暂停。10 条记录的文件写入日历耗时与记录耗时存在大差距；文件 mtime 是间接证据，不能逐条判定休眠发生在提交前还是提交后，因此不回写旧评分，也不从该批得出正式时间效应。审计见 [计时疑点记录](../reports/go_sleep_clock_audit_20261031.json)。

新协议 `continuous_deadline_v1` 用包含休眠的单调钟，等待期间每至多 0.25 秒和完成时复核，休眠差超过 1 秒计环境中断并停止扩量，校准受休眠影响也直接失败。Mac 进程运行期间用 `caffeinate -i` 阻止自动休眠。全量离线验证、18 次新诊断、216 次新开发之后，才按原准入规则进入 1080 次正式；不以修复为由放宽准入。正式效应与固定上下文探针仍按原方案分别报告。


连续钟新诊断 18 次中 16 正确，GLM 表格证据多报导致未通过基础门槛。按公开题意澄清共同 system prompt 的精确证据集合要求，排除关联查询中无匹配的行；三个模型同样修改，不调整答案或评分门槛。修订后重新通过离线验证与 18 次诊断，才扩至完整开发。该修订属于模型与框架组合的变化，结果不得与旧提示版本合并。

### 重复请求描述指标的精确定义

在实际探针采样前登记：比较工具名及完整 arguments 是否与先前已有结果的请求完全相同，忽略宿主未用的额外顶层字段。不同参数形式即使返回相同记录，也不自动判为重复；重复不等于错误或低效。冻结探针的原始分类保留，完整采样后由 `scripts/probe_request_report.py` 输出派生分类和与原标签的差异；不改模型输入或采样清单、不丢超时、不重新采样。该规则来自主实验中的字段保真审计，不依据探针结果或 C−B 差值选择。
