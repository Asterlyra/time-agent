# OpenCode Go 模型实验接入建议

日期：2026-10-30。本文是检查后的执行建议；未接入账户、未发送收费模型请求、未修改实验代码或解除正式运行门禁。

后续已补充 [Agent 构造说明](../docs/Agent构造说明.md) 与 [基于现有数据的后续实验计划](../docs/后续实验计划_20261030.md)。本文保留接入路线比较，分阶段执行数量和开发准入规则以新计划为准。

## 1. 建议结论

主实验采用现有 Python 串行决策循环，通过薄 API 适配层调用三个固定模型。OpenCode 自定义 agent 适合补充复现，用来检查方法在实际 coding-agent 框架中的表现。首轮不要混合多个 agent 框架。

Go 的 API 技术上支持其他客户端，但官方将其定位为 coding-agent 流量。当前表格与证据检索基准是否适用这一套餐，公开文档不能直接确认。不能通过把客户端改名、伪装成 OpenCode 或增加无意义编码步骤解决此问题。若服务方不覆盖此类实验，主实验使用允许该用途的按量 API；实验协议无需随计费渠道改变。改用 OpenCode 本身也不能自动解决用途问题。

## 2. 当前实现与证据

- `src/runner_v2.py` 管理 episode 的墙钟截止、模型决策、工具执行、延迟注入、提交与确定性评分；通过 `model.decide(observation, history)` 对接模型，因此可保留现有循环，仅替换适配器。
- `src/conditions.py` 实现 A/B/C：A 无额外摘要，B 固定使用预校准均值，C 使用最近最多三条已完成同类工具耗时；没有新样本时 C 回退到预校准。
- `tasks/data_v4.py` 在 v3 上扩展无答案摘要搜索，表格继续分页；数据生成、公开工具和私有评分存在清楚的接口分工。评分仍由宿主执行，不能把私有数据发给模型。
- `scripts/run_v5_pilot.py` 使用 v4 任务、v2 runner，但仍绑定 Codex MXC。180 秒预算、36 秒变化点，2 秒/15 秒工具目标耗时；只有两道开发题，A/B/C 共六次。
- `reports/v5_pilot_findings.md` 记录 4/6 截止前正确，另一次证据选择错误、一次工具超时。这只能支持继续开发验证，不能支持动态参考更优。
- `scripts/run_formal.py` 仍绑定旧 runner/v2 任务与单个 Luna 模型，并显式阻断正式执行。它不是当前 v5 流程的多模型正式入口，不能只替换模型名便启动。
- `scripts/matrix.py` 已有配对清单、冻结哈希及不覆盖式运行记录；`scripts/analyze_matrix.py` 已有按任务聚类的配对 bootstrap。存在缺失记录时，当前分析器采用完整配对子集，必须明确这一选择性限制。
- 本机 `python3 -m unittest discover -s tests -q`：72 项，5 项报错、1 项跳过；五项报错来自 MXC 适配器要求 Windows。本机实际 Python 为 3.9，README 声明 3.13。这是当前环境下的检查结果，不能当作建议 API 适配器已获验证。

调用链：开发/正式入口选择任务和清单 → runner 构造公共观察与时间反馈 → 模型返回一个 JSON 动作 → 宿主执行白名单工具并注入延迟 → 工具结果加入历史 → 下一轮决策；首次格式有效提交或截止后终止，宿主离线评分。

现有设计将策略决策与工具执行分开，有利于控制延迟和防止答案泄漏；CLI 适配器带来的框架指令、进程启动/收尾和平台隔离问题，则会影响可比性。

## 3. 三条接入路线

| 路线 | 适用性与代价 | 建议 |
|---|---|---|
| 现有 Python agent + 薄 API 适配层 | 精确控制消息、串行工具、计时、取消、重试；需实现和验证适配层；Go 用途适用性待核对 | 主实验首选；必要时用按量渠道 |
| OpenCode 常驻服务 + 自定义实验 agent | 可用其框架接入模型；仍需控制内置工具、提示、压缩和辅助请求，审计额外开销 | 补充复现，或明确将研究对象限定为 OpenCode agent |
| Go + Hermes/Pi 等通用 agent | 官方有其他 coding-agent 客户端接入支持；但引入新的循环、历史管理和工具语义 | 首轮不增加这个变量 |

若使用 OpenCode，采用常驻 `opencode serve`，每个 episode 新建独立会话；配置单一自定义 agent，提供实验工具，关闭无关文件、shell、网络和子 agent 能力，检查标题、摘要、压缩等辅助请求。配置之外仍需独立验证执行边界。服务启动可以在 episode 外，episode 内所有请求和循环开销都计入预算。不要逐轮重新启动 CLI。

## 4. 推荐模型

首轮保留原方案 GLM、Qwen、DeepSeek 三个家族，以预算较适合多轮实验的候选开始：

| 模型 | 官方模型 ID | 选择理由 |
|---|---|---|
| GLM 5.3 Flash | `glm-5.3-flash` | GLM 家族候选，适合先检查多轮协议与预算可行性 |
| Qwen3.8 Flash | `qwen3.8-flash` | 保留 Qwen 家族，检查不同模型下时间反馈的效果 |
| DeepSeek V4.1 Flash | `deepseek-v4.1-flash` | 保留 DeepSeek 家族，形成三家族复现 |

这些是待预跑的候选，不是已经证明最快或效果最好的模型。固定精确模型 ID、可见服务版本、推理模式、输出上限、温度及接口；不支持的参数要记为不支持，不能假定不同厂商同名参数代表同等推理量。

可选第四模型 `gpt-6-luna`，仅作后续扩展，便于与旧开发流程衔接。即便名称相同，Go 路由与 Codex CLI 的供应、提示及框架不同，历史结果也不能直接并入新实验。不要给不同模型分别配置不同的 agent 框架。

官方目录中 Qwen3.8 Flash 的原生接口是 Anthropic Messages，另外两个候选是 Chat Completions。建议保留统一动作协议，在适配层处理原生 API 差异，避免未经验证的跨协议转换。供应方支持转换接口，但这不能替代协议一致性验证。

## 5. 接口与套餐核对

官方 Harness 文档给出的 Go 基址为 `https://opencode.ai/inference/go`，例如 Chat Completions 路径为 `/openai/v1/chat/completions`。客户端应使用真实的自有 User-Agent；同一 episode 的所有轮次使用同一个 `x-opencode-session`，不同 episode 使用独立 ID。

Go 存在按模型计算的五小时、周、月限额；不能理解为无限 API 调用。实际运行前核对账户可见模型、剩余额度、超限行为与费用上限，禁用自动付费溢出（如账户提供该选项）。记录响应中的 token、缓存、billing_source 与 allowance，缺失则保留 null；套餐实际收费为零不代表不消耗额度。

本次仅查阅公开官方资料，未验证用户账户权限和余额。无鉴权请求公共模型列表返回 403，也不能由此推断用户密钥无权限。DeepSeek 还需核对账户的区域设置；本文未修改该设置。

## 6. 分阶段运行

### 阶段一：协议与边界验证

使用模拟响应验证完整动作到达时刻、截止时取消、格式错误、429/5xx、一次重试、首次有效提交终止与日志恢复；验证模型只能收到公开题面、当前工具结果及允许的时间反馈。密钥仅在宿主适配层持有。

三个模型各用两类中的一道开发题做冒烟检查，约 6 个 episode；宽松预算只用于确认能调用和完成题目，不能混入正式结果。核对一轮仅产生一个允许动作，无文件读取、网络工具或额外 agent。

### 阶段二：开发集校准

使用当前八道开发题：3 模型 × 8 题 × 3 条件 × 3 延迟模式 × 1 次 = 216 个 episode。

以 v5 的 180 秒、20% 变化点、2/15 秒延迟、窗口 3、最多 20 步为候选，重新检查：

- 各模型能否完成基本任务，是否存在严重地板/天花板效应。
- 新阶段同类工具反馈能否返回，之后是否还有至少一次决策机会。
- C 的工具分类统计在变化后是否有实际更新机会。
- 模型请求时间、工具等待、协议修复和框架开销各占多少。
- 查询与证据返回能否允许不同成本的有效路径；不能靠强制每题固定调用次数制造“适应”。

调整仅依据开发集的可行性标准，保留所有版本与记录；禁止依据 C−B 胜负选择时间预算、任务或模型。对三个模型尽量使用共同预算和共同任务结构；若有例外，要预先列为独立分析。

人工复核每类至少三道题，并检查证据集合规则，尤其是数值正确但证据不合规的情况。重复种子不能弥补任务结构单一，应尽量增加实质不同的信息获取和筛选结构。

### 阶段三：冻结后正式运行

完整矩阵：3 模型 × 20 测试题 × A/B/C × 3 延迟模式 × 2 次重复 = 1,080 个 episode，每模型 360 次。180 秒上限对应串行预算总和 54 小时；三模型各串行、全局并发 3 时，理想上限约 18 小时，另加校准、限额等待、恢复与分析。不是吞吐承诺。

资源不足时，在查看正式效果前缩减为两类各五题，共 540 次；相同并发下理想预算上限约 9 小时。应根据开发集实测调用轮数、token、额度与吞吐确认资源，不能仅靠 episode 数推断套餐足够。

每模型并发先固定为 1，同模型内交错 A/B/C，按任务/模式/重复编号配对并随机化顺序。同一配对块共享任务与预校准，动态统计只属于单个 episode。开始后不为某模型单独放宽截止；服务异常、重试、暂停与补跑规则在冻结前写明，不静默覆盖失败。

## 7. 指标和可支持的结论

主指标：截止前答案数值与证据同时正确的比例。主比较：fast_to_slow 下 C−B；同时报告各模型结果与模型等权汇总。C−A、其他模式及任务类别为次要比较。

按任务实例聚类做配对 bootstrap，保留重复及模型对应关系，给出 95% 区间；独立任务只有 20 个，不能把两次重复当成 40 个独立任务。明确缺失记录及分母，服务故障保留并单列。

辅助指标包括模型请求耗时、已完成和删失的工具等待、工具次数、提交率、错误类型、超时阶段与服务故障。收到新阶段反馈后的行为用于描述机制，不能仅挑“观察到变化”的任务作为主分析样本。

只有总成功率变化不足以证明策略适应。需要结合变化后的动作轨迹，判断是否减少低价值查询、改变查询路径或及时提交。三个固定模型的结果也不能推广为所有 agent 或所有模型的普遍规律。

## 8. 实现工作边界

确认接入路线后，新增 API 适配层与多模型开发入口，复用 runner_v2、v4 任务、清单和日志；完成跨平台协议与隔离检查后，再建立与最新流水线一致的正式入口。保留旧实验原始记录和现有 fail-closed 门禁。

本文未实施这些变更。正式代码改造涉及外部服务和运行架构，需要先确定路线；目前建议选择“统一 Python agent + API”，Go 用途不适用时沿用同一协议切换到允许实验用途的按量渠道。
