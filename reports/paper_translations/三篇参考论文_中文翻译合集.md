## 摘要

我们研究小型 LLM Agent 能否在明确的墙钟时间预算下有效工作，也就是既遵守分配到的运行时间，又高效地利用可用时间。我们在两类 Agent 基准上评估：在 MLE-Bench Lite 的五个竞赛任务上使用 Qwen3.6-27B，在 Zork I（Jericho）上使用 Qwen3-4B。之所以选择这两类环境，是因为额外计算时间能够实质性地提升性能。在最简单的设置中——只在提示词里说明预算——Agent 无法把给定预算转化为受控的时间使用。这些失败既源于时间感知的缺口（运行框架没有提供计时反馈），也源于 Agent 无法可靠预判动作时长，以及缺少“把可用时间映射到合适策略”的学习能力。我们研究了两类互补的干预：一类是基于运行框架、暴露时间信息并执行截止时间的机制；另一类是用预算感知奖励进行的强化学习。通过运行框架注入时间信息，可以显著提高 Qwen3.6-27B 的预算遵守率，且未观察到可测的性能损失；执行钩子则进一步收紧遵守程度。使用 GRPO 的强化学习在 Zork I 上达到接近完美的预算遵守，并能泛化到训练中未见过的预算；但在 MLE-Bench 上，它相对未经训练的框架并没有提升任务表现。即使 Agent 已经学会遵守预算，它们仍然无法利用额外时间来提升任务表现。经 RL 训练的策略学会了何时停止，却经常用重复动作填满额外时间；在多个预算上做 GRPO 训练，还会让策略坍缩到针对最短预算学到的策略。我们的结果揭示了“时间遵守”与“有效时间分配”之间的缺口，而这仍是预算条件 Agent 的核心挑战。

## 1 引言

**图注：图 1** （左侧两图）Qwen3.6-27B 在 MLE-Bench 上的平均质量（排行榜百分位）与平均墙钟用时关系：左图为仅在提示词中说明预算，右图为加入执行框架后的结果。颜色表示声明的预算，虚线标出预算值。（右侧两图）在 15 分钟 MLE-Bench 任务中进行的 episode 中期时间估计。研究者询问 Agent 已工作多久、整次运行总共会花多久，并将其回答与真实值对比；虚线对角线表示完美估计。空心标记表示上下文中有时钟，实心标记表示没有时钟。

当 AI Agent 承担涉及规划、工具使用和迭代改进的复杂长程任务时，除了最终解的质量外，**完成任务所花的时间**也成为其行为的重要维度。Agent 应当能在明确的墙钟时间预算下有效工作，原因有二。第一，Agent 面临外部约束：用户应能控制任务端到端耗时；嵌入大型系统的 Agent 也必须满足截止时间，以便与其他组件协调。第二，对许多任务而言，时间与质量是一致的。在 ML 工程这类搜索密集型问题中，更多时间让 Agent 可以探索更多架构、超参数或候选解，因此目标并不是让 Agent 尽可能快。与此同时，不同用户对“解的质量与时间”的权衡不同，而时间预算正是用户表达这一权衡的方式。

我们对预算约束下的 Agent 提出两点要求，分别称为**遵守（adherence）**和**有效利用（productive use）**。遵守是指 Agent 在规定时间内返回解；运行框架可以用硬中断强制实现这一点，从而迫使 Agent 一直工作到截止时间。有效利用是指 Agent 把这些时间用好，用额外预算改进解，而不是提前停止或用不必要的动作填充运行时间。一个具体检验是：预算增加时任务表现是否提升？如果 Agent 在紧预算和宽裕预算下取得同样质量，那么额外时间就没有被转化为更好的解。此外，这些任务很大程度上受工具调用延迟支配；我们还要检验模型能否同时纳入工具延迟和生成时间，以保持在预算内。

当前 Agent 即使在最简单的设置下也无法遵守预算：预算只在提示词中说明，运行框架不提供已用时间反馈。在 MLE-Bench 上，Qwen3.6-27B 不能有效利用分配时间（图 1 左；表 1）。无论给定预算多少，Qwen3.6-27B 都运行约十分钟：在 8 分钟预算下超时，在 60 分钟预算下却只用了很小一部分。

这些失败反映了模型在“能观察到什么”和“能预测什么”上的具体缺口。模型上下文中没有任何信息表明已经流逝的墙钟时间；token 数又是很差的代理量，因为它取决于硬件和推理配置。直接探测模型可以确认这一点。在一个 15 分钟任务的 episode 中途询问已经工作了多久，Qwen3.6-27B 对自身已用时间的判断严重偏离真实值（图 1 右；附录表 9）。Agent 也不能可靠预测自己的动作会花多久，这对训练任务这类长时工具调用尤其重要；即使上下文里有时钟，对本次运行剩余时长和总时长的预测仍相差很远。我们因此假设：即便 Agent 拥有完美的计时信息，它仍然必须学会把可用时间映射到合适计划。

我们研究两类互补干预：基于运行框架的干预和基于学习的干预。运行框架干预用来填补观察缺口：逐动作时钟和周期性提醒报告剩余预算以及每个动作的时间成本；可选执行模式则通过限制或拒绝过长命令来守住截止时间。基于学习的干预针对规划缺口。我们还探索用预算感知奖励做强化学习（GRPO），作为把时间—质量权衡直接内化的一步初步尝试。我们在两个“额外时间能实质改善结果”的 Agent 环境中评估：MLE-Bench Lite 的五个竞赛和 Zork I（Jericho）。二者在动作结构、反馈密度以及时间如何转化为质量上均不同。我们选择少量任务，使不同预算应偏向不同策略，并详细分析失败模式。

本文将时间预算问题拆成**遵守**和**有效利用**两部分，二者难度差异很大。我们表明，在本文设置中遵守基本可解。运行框架把 Qwen3.6-27B 的用时从预算的 161% 带到预算内，且相对无框架运行的测量范围内没有质量损失；RL 在 Zork I 上实现接近精确的遵守，并能泛化到留出预算；不过在搜索空间大得多的 MLE-Bench 上训练效果较弱。然而，有效利用要难得多。我们表明，按时完成的 Agent 并不能把额外时间转化为更好结果；学会何时停止的 RL 策略会用不会带来更好任务结果的动作填满额外时间。

## 2 相关工作

### 预算感知与时间感知的测试时扩展

Lin 等人 [1] 把预算感知形式化为渐进区间估计：Agent 在每一步预测剩余预算的上下界，并发现前沿 Agent 会持续过度乐观地估计剩余预算。他们的 SFT+RL 训练改善了早停行为，但精确校准仍然困难。我们的工作关注墙钟时间而非 token 预算，并研究从提示词、运行框架执行到 RL 的逐步演进，而不是单一训练方法。Li 等人 [2] 提出无需训练的预算感知价值树搜索，在预算耗尽时从探索转向利用；McCleary 与 Ghawaly [3] 测量固定约束下搜索深度、检索策略和完成预算如何影响准确率。二者都在 token 或工具调用层面操作。我们研究墙钟时间，因为其随机动作时长无法被 token 计数捕捉。

Snell 等人 [4] 表明，计算最优的测试时扩展策略可以胜过规模大 14 倍的模型，但他们假设预算无限。Ma 等人 [5] 用 Timely-Eval 基准和 Timely-RL 训练方法，以墙钟时间重新定义测试时扩展，并发现现有模型无法让推理适应时间预算。Ma 等人聚焦于单一 RL 干预，而我们比较提示词、运行框架执行和 RL 这一递进序列。Paglieri 等人 [6] 用 SFT 和 RL 教 Agent 判断何时值得规划。我们研究整个策略应如何适应时间预算，并发现 RL 学会了何时停止，却没有学会在更多时间下应如何改变做法。

### 预算约束与受约束强化学习

受约束马尔可夫决策过程（CMDP）[7] 形式化了在成本约束下最大化奖励的问题。Carrara 等人 [8] 将其扩展到 Budgeted MDP：让单一策略以预算为条件，从而无需重新训练即可求解任意预算水平的 CMDP；我们的 RL 阶段采用了这一思想。我们的成本信号——墙钟时间——是随机且不可预测的，而经典 BMDP 假设状态—动作对的成本函数已知。McMahan 与 Zhu [9] 要求预算在任何时刻都不能被违反；这更接近我们的设置，因为 Agent 在第 t 步超时后无法在第 t+1 步撤销。他们关于“在任意时刻约束下马尔可夫策略不充分”的结论，支持我们把剩余预算注入 Agent 上下文的选择。Achille [10] 认为时间才是扩展推理模型时的关键优化量，并警告一种失败模式：奖励驱动的模型会暴力搜索解，却没有获得可迁移策略。我们经 RL 训练的策略所表现出的“记忆前缀 + 无效动作”行为，正符合这种失败模式。

### LLM 的强化学习

Group Relative Policy Optimization（GRPO）[11] 最初为 DeepSeek-Math 提出，并用于 DeepSeek-R1 [12]。它针对每个任务采样一组 rollout，并在组内归一化奖励，从而避免单独的价值网络。我们采用 GRPO，因为这种归一化能处理“一次在多个预算水平上训练”所产生的多峰奖励分布。

## 3 实验设置

### 3.1 数据集

我们在两个环境中评估时间预算下的 Agent 行为：用 MLE-Bench 进行机器学习工程，用 Jericho Zork 进行文本游戏。选择二者的原因是：任务表现会随墙钟时间显著变化；它们允许在不同预算水平采用多种有效策略；并且它们会对部分完成的工作给出分级评分。

#### MLE-Bench Lite

MLE-Bench [13] 用来自 Kaggle 竞赛的端到端机器学习任务评估 Agent。我们使用 MLE-Bench Lite——一个含 22 个竞赛的子集——并按两项标准从中选择 5 个任务。第一，任务必须在不同时间尺度上允许性质不同的策略（例如快速基线 vs. 迭代式特征工程）。第二，预实验必须显示：在 10 到 25 分钟的不同时间预算下，得分存在不可忽略的方差。每个任务都要求 Agent 检查数据、编写并执行建模代码、迭代实验并生成有效提交。该环境非常适合研究时间感知 Agent，因为更多墙钟时间可以支持不同活动：短预算也许只够训练一个基线模型，较长预算则允许进行数据分析、特征工程、模型选择、超参数调优和更长的训练。我们使用 MLE-Bench Lite 的五竞赛子集：dog-breed identification 和 dogs-vs-cats（图像分类）、leaf classification（基于提取的叶片图像特征做物种分类）、spooky-author identification（文本分类）以及 NOMAD 2018 transparent-conductor prediction（表格回归）。

我们使用 Qwen3.6-27B [14] 作为基础语言模型，通过 OpenCode Agent 框架运行。对于 RL 训练，我们使用内部工具从 Agent rollout 中获取 TITO（Training In, Training Out）格式数据，把轨迹转换为 GRPO 训练样本。我们改变墙钟预算，并测量 Agent 轨迹与最终任务表现如何随可用时间变化。

#### Jericho（Zork I）

Jericho [15] 是交互式小说环境，Agent 通过自然语言动作与文本游戏交互。所有实验均使用 `zork1`。每一步，模型观察当前游戏状态、生成动作并接收结果观察。额外时间直接转化为更多探索步骤，性能取决于 Agent 发现了多少世界地图、解决了多少谜题。

评估时，我们在轻量 Agent 循环中使用 Qwen3-4B [14]、Qwen3.5-9B 和 Qwen3.8-27B [16]，并关闭 thinking 模式。模型反复接收观察、生成下一动作并观察结果，直到轨迹终止或时间预算耗尽。我们把任务奖励定义为归一化游戏得分 `R_task`，它提供密集且可跨轨迹比较的进度度量（Zork I 中 `max_score=350`）。我们用该环境进行 Jericho Zork1 的 RL 实验，训练模型使其行为以不同时间预算为条件，并在探索、任务进度与预算遵守之间权衡。

#### MLE-Bench

仅靠提示词对指定时间预算的遵守很弱。由于不能直接访问墙钟时间，模型无法可靠估计先前的动作、工具调用或推理步骤花了多久。模型原则上可以通过查询系统时钟自行跟踪时间，但我们没有观察到这种行为。消耗的总墙钟时间基本不受提示词预算影响：在仅提示词的 MLE-Bench 上，Agent 平均使用了 15 分钟预算的 161%，只有 15% 的运行在声明上限内完成（表 2）。

#### Zork I

仅在提示词中说明时间预算，不能带来可靠的预算遵守。如表 6 中“Budget in Prompt”各行所示，所有模型都大幅超出声明预算，往往一直运行到 2 倍预算的硬截止才被终止（见图 2b）。多数模型的任务表现也仍接近零。这种行为可以预期：模型没有关于墙钟生成速度的直接概念，也没有收到执行过程中已流逝多少时间的反馈。因此，声明预算只是自然语言中的约束；开箱即用的模型并不具备应用这一约束的能力。

### 4.2 通过运行框架干预

#### MLE-Bench

通过运行框架暴露已用时间，使 Agent 明显更响应预算。三个钩子（表 3）报告剩余时间和生成本身的时间成本，但不规定任何动作。这把消耗时间从声明预算的 161.4% 降至 99.7%，质量没有可测变化（47.5 到 47.0 百分位，处于误差范围内），并把产生有效提交的运行比例从 78% 提高到 88%（表 2）。

**表 3：运行框架钩子。** 前三个钩子只向 Agent 读取的内容中添加信息。两种执行模式会改变动作本身，且从不同时使用。

| 钩子 | 触发时机 | 作用 |
|---|---|---|
| 每工具时钟 | 每次工具调用之后 | 在 Agent 看到的结果中加入剩余时间 |
| 周期提醒 | 按固定时间间隔 | 即使命令仍在运行，也报告剩余时间 |
| 生成计时 | 每次工具调用之后 | 报告模型在动作前生成文本花了多久 |
| 执行（截断） | shell 命令运行之前 | 缩短命令的时间限制，使其在截止前停止；命令仍会运行，但会被截断 |
| 执行（拒绝） | shell 命令运行之前 | 阻止命令执行并返回解释信息，迫使 Agent 选择成本更低的动作 |

主要失败模式是：当 Agent 意识到剩余时间不多时，却启动了一个耗时超过剩余预算的工具调用（例如训练的超时设置比剩余时间更长）。由于工具调用时长可变且难以预测，Agent 往往在超出预算前没有机会再采取行动。即使被提示把工具调用放到后台以便中断，模型仍无法稳定地及时停止。

因此，我们加入执行钩子：在每条 shell 命令运行前检查它，比较 Agent 为该命令设置的时间限制与剩余时间。由于命令经常没有设置限制，缺失限制按运行框架默认超时处理。执行机制进一步减少了超时，但以小幅质量损失为代价。按时率提高，质量略有下降。质量代价并不意外：未执行约束时，模型把超时的时间转化为得分，而执行机制拿走了这部分时间。缩短命令限制保住了大部分无约束时的质量，并产生了我们测得的最高有效提交率（90%）。直接阻止命令则更贴近预算，但降低了有效格式提交率并增加了交互步数，因为 Agent 会用更小的限制重新发出被阻止的命令。

即使没有 RL 训练，只要给 Agent 一个时钟，它就会让已用时间随声明预算缩放。附录图 4 展示了四种预算下的时间和质量分布。每种预算下质量都散布在整个百分位范围内，并没有随预算增长而上升的趋势。

#### Zork I

为了给 Agent 明确的已用时间感知，我们在 Zork 中引入三种运行框架级干预。第一，**Clock Tool** 允许模型发起 `time_elapsed` 工具调用，返回形如 `[time used: x s of B s budget]` 的消息。第二，**Clock Tool++** 使用相同工具接口，但在提示词中提供更多关于何时、如何查询的指导，并给出上下文示例。第三，**Auto-Clock** 框架让运行框架在每轮交互后自动把同样的已用时间消息追加到上下文，从而不再需要模型主动请求计时信息。

基本的 Clock Tool 对遵守几乎没有改善（见图 2 和表 6）。即使模型现在能访问墙钟时间，它仍需决定何时查询工具，而模型往往调用得不够频繁，使反馈无法发挥作用。因此，多数模型在短预算下仍会大幅超时。但在 Clock Tool++ 下，模型调用工具的频率高得多（附录表 8），由此增加的计时反馈带来相对更好的预算遵守。最强的遵守来自 Auto-Clock：它在每一轮之后把计时信息推入上下文，而不是等模型请求。在这一干预下，多数模型能更紧地跟踪可用预算。但其局限是：运行框架反馈只在两次生成之间可用；如果单次生成本身就消耗了很大一部分预算，框架只能等该次生成完成后才能干预。这一效应在 9B 和 27B 等较大模型上尤其明显。另一个有趣观察是：尽管预算遵守显著改善，所有预算下得分仍低于 5。这说明获得时间反馈能帮助模型判断何时停止，却没有教会它如何调整策略。因此，我们在图 2(a) 的前沿中没有观察到有意义的质量—预算权衡。

### 4.3 通过 RL 训练干预

#### 4.3.1 MLE-Bench

**目标。** 我们使用 GRPO [11] 训练。设 `B` 为预算，`t` 为已用墙钟时间，`q ∈ [0,1]` 为留下的提交的归一化任务得分。奖励为：

$$
R(q,t)=
\begin{cases}
q+c_{\mathrm{time}}, & \text{已提交且 }t\le B,\\[4pt]
\alpha q-p(t-B), & \text{已提交且 }t>B,\\[4pt]
-c_{\mathrm{fail}}, & \text{未提交},
\end{cases}
\tag{1}
$$

其中 `c_time > 0` 是在预算内完成的奖励，`α ∈ (0,1)` 是迟到时保留的质量比例，`p > 0` 是每超时一秒的惩罚，`c_fail > 0` 是没有任何产出的代价。常数设置保证：在质量相同时，按时完成总是优于迟到完成；而没有任何产出总是最差。

**结果。** 表 2 展示了 MLE-Bench 上的结果。训练未能超过其训练时所处运行框架的表现。训练确实把交互步数从 20.3 降到 18.9，改善了执行插件引入的重试行为。

训练后的策略会让投入随预算缩放。无论设定预算为何，每次运行使用预算的比例都保持在 0.87 到 0.93 之间。另一方面，约四分之一的按时提交得分并不比随机猜测更好，而且当质量 `q` 的权重提高到三倍时，这一比例也未下降。GRPO 训练没能提升模型在 MLE-Bench 任务子集上的表现，但确实强化了其按预算运行的能力。

#### 4.3.2 Zork I

**目标。** 设 `B` 为提示词中逐字给出的秒数预算，`t` 为 episode 消耗的墙钟时间，`s = score/score_max ∈ [0,1]` 为 episode 结束时 Agent 的归一化游戏得分（Zork I 中 `score_max=350`）。游戏得分直接从实时游戏中读取。奖励必须提供停止的理由，因为 Agent 可以通过 `quit` 自行结束 episode，否则会一直玩到 180 秒墙钟硬终止或轮数上限。下面描述我们探索的奖励函数。所有奖励函数都采用：

$$
R(s,t)=\left[s+\lambda b(t;B)\right]\cdot g(t;B)
\tag{2}
$$

其中 `b ∈ [0,1]` 是时间奖励，`g ∈ {0,1}` 是使全部奖励归零的门控，`λ > 0` 是时间相对于得分的权重（得分始终权重为 1；我们使用 `λ=0.1`）。四种方案详见附录表 10，它们只在 `b` 和 `g` 上不同：(i) Cutoff 是纯门控、无奖励；(ii) Linear 和 (iii) Gaussian 是在 `t=B` 处的平滑峰值，奖励从两侧接近预算；(iv) Step 是粗略斜坡，按预算的十分之一为单位奖励已用时间，并在超过 1.1B 后将 episode 奖励归零。我们选择 step-wise 奖励训练 RL 模型。尽管各种塑形奖励表现大致相当，step-wise 在收敛速度、任务得分和预算遵守之间取得最佳总体平衡（表 7）。我们通过在每个 GRPO 步从 0 到 16 秒均匀采样时间预算来训练 RL 策略，并用 step-wise 奖励优化。该训练流程同时应用于 AutoClock 和 Clock Tool++ 干预，所得运行分别称为 RL + AutoClock 和 RL + Clock Tool++。两种设置下，策略都学会保持在分配预算内，同时提升该预算下的任务表现并推动前沿（见图 2a）。不过 RL + Clock Tool++ 的得分低于 RL + AutoClock（图 2、表 6）。我们将差距归因于主动查时的开销：RL + Clock Tool++ 约 50% 的轮次用于查询时钟，留给任务推进的动作更少。尽管有此低效，两个策略都实现了很强的遵守，生成通常在指定预算的 ±15% 内终止。

**时钟可泛化，玩法不能泛化：** 我们还使用离散预算而不是连续均匀采样来训练同一策略，从而可以研究 15、30、60、90 秒等更长时域。每次 rollout 从预定义预算集合（称为 budget mix）中分配一个预算，并在提示词中把对应预算给模型。原则上，训练中交错多个预算应促使策略以可用时间为条件，并利用更大预算做更广泛探索。训练推进时，不同时域下的预算遵守变得接近完美。然而，策略坍缩到针对最小预算学到的策略（图 3）。不同预算的轨迹在已用墙钟时间上明显分开，但它们的游戏得分在整个训练过程中沿近乎相同的趋势变化。因此，模型学会了针对每个请求预算何时停止，却没有学会如何有效利用额外时间提升任务表现。

**图注：** (a) Budget mix `{15,30,60,90}`。

## 5 局限性

**跨预算的策略坍缩。** 训练后的策略学会紧密遵守声明预算，却没有为不同预算做不同规划。在 Zork 中，不同预算下的 rollout 以相同的记忆动作序列开局，并达到相同得分，与给定预算无关。预算只改变 Agent 在退出前用填充动作填充多久。混合预算训练本意是防止这种坍缩，但它只成功帮助模型把“停止”泛化到多个预算。MLE-Bench 上也有相同模式：额外时间买到更多训练模型尝试，却没提高最终得分。另见“通过无效动作实现预算遵守”一节。

**固定环境中的记忆化。** 在单一游戏、固定初始状态上训练，使记忆化成为提高得分最便宜的路径。Zork 策略收敛到一个回忆出的攻略前缀，收集固定数量的分数，之后再也找不到新得分。当把有效动作而非模型自己的输出反馈给模型时，同一检查点得分低得多，确认所学行为连很小的变化都无法承受。奖励结构加剧了这个问题：它为已用时间定价，却不为探索定价；因此一旦存在得分前缀，偏离它就没有收益。奖励也不区分被拒绝动作与有产出动作，训练后的策略会用重复命令填充剩余时间。因此，预算利用率只能证明模型能按时停止，不能证明它多好地利用了分配时间。我们在附录讨论这些机制，以及 MLE-Bench 上随机动作时长带来的第三类噪声。

**评估范围。** 我们的实验使用两个模型（Qwen3-4B、Qwen3.6-27B）和两个环境，Zork 上的 RL 实验只在单一游戏上训练。这些发现能否推广到前沿规模模型、具有更丰富策略空间的环境，仍待研究。MLE-Bench 子集只含五个竞赛，限制了训练中策略遇到的任务结构多样性。跨更多模型、环境类型和任务数量的更广泛评估会增强这里结论的可信度。

## 6 结论

我们研究了 LLM Agent 能否在明确时间预算下推理和行动，并比较两类干预：(i) 暴露或执行时间信息的运行框架机制；(ii) 直接优化预算条件行为的 GRPO 训练。仅在提示词中说明时间预算并不足够：开箱即用的 Agent 难以估计动作时长，在 Zork 中小预算下超时可达 2 倍，在 MLE-Bench 上超时 61%。相反，通过 Agent 运行框架暴露时间可显著改善遵守。信息性时钟把两个环境的超时降至接近零，且任务质量几乎没有可测损失；更严格的执行钩子进一步收紧遵守，但带来适度性能代价。

GRPO 训练进一步改善预算遵守。在 Zork 上，训练策略在 5 到 90 秒的预算范围内与请求预算的偏差在 0.2 秒以内，包括训练中未见的四个留出预算。在 MLE-Bench 上，训练策略稳定使用分配预算的 0.87 到 0.93。在较小预算下，RL 还向外推动成本—得分前沿，同时改善遵守和任务表现。然而，这种改善并不能统一扩展到更大预算。在这些稀疏奖励场景中，当前目标几乎没有为更深探索或性质不同的策略提供激励。在 Zork 上，策略收敛到固定的高奖励前缀，并把额外时间花在无产出的动作上，导致更大预算下得分饱和在 45/350。类似地，在 MLE-Bench 上，额外时间导致对基本相同训练流程的更多尝试，却没有提升提交质量。

我们表明，这些结果揭示了预算遵守与有效预算分配（即在获得更多时间时改变行为的能力）之间的区别。解释这些发现时需考虑三项局限：跨预算策略坍缩、固定训练环境与稀疏奖励导致的记忆化，以及模型和任务评估范围有限。可能方向包括：奖励新颖状态而非已用时间的探索感知奖励；防止记忆化替代搜索的环境变化；以及区分重复尝试与真正不同策略的奖励项。遵守（RL 已能解决）与有效时间分配（仍未解决）之间的缺口，定义了预算条件 Agent 的核心挑战。

### A.1 奖励结构与探索激励

奖励只是最终得分和已用时间的函数，因此探索没有价格。在 Zork 中，一旦存在得分前缀，偏离它就是主动冒险。我们的 4B 模型通常最多达到约 `45/350≈0.129` 的得分。取 `λ=0.1` 时，时间项最高值约为 0.100，已经与策略取得的得分项相当。此外，Zork 奖励相对离散，有意义的提升常常需要多拿好几分；例如多拿 5 分只让得分项增加 `5/350≈0.014`。因此，完美的预算遵守大约相当于一次真正的 5 分发现价值的七倍，而且任何消耗时钟的 token 序列都能确定性地获得它。要修正这一点，需要加入为新颖性付酬的项（首次访问奖励、攻略覆盖率、基于到未到达状态距离的势函数塑形），并让环境在 episode 间变化，使回忆不能替代搜索。

在 MLE-Bench 上，类似问题是奖励不区分对同一策略的重复尝试与真正不同的方法。如果最优提交得分相同，那么较长预算下三次提交同一基线的策略，与逐步尝试更复杂方法的策略得到同样奖励。

### A.2 通过无效动作实现预算遵守

由于 Zork 的时间项只由墙钟满足，策略学会了通过发出解析器拒绝的命令来消耗时钟。在一次特定训练的第 500 步，填充词是 `forward`，Zork 回复 `I don't know the word "forward"`。它在 128 个 rollout 中的 127 个里出现，紧接记忆前缀结束之后；在 `B=15` 时占轮数的 45%，在 `B=90` 时占 88%。预算几乎完全是通过重复一个不推进任何东西的动作来满足的，误差在 0.2 秒内，因为已用时间丈量的是墙钟延迟，与动作是否被接受无关；被拒绝的命令消耗的生成时间与有效动作相同。

这意味着“使用了 99% 的预算”不应读作“99% 的预算用于工作”。任何关于努力分配的断言都需要衡量有用时间（改变游戏状态的轮次、有效命令率，或花在被接受动作上的 token）。这个失败模式用错误诊断很容易漏掉：我们的重复检测器对这些运行只报告 1.0–1.5 轮的尾部相同动作，因为它测量的是与最后动作（`quit`）相同的尾部，所以数百个连续无效动作落在窗口之外。惩罚无效动作或只计入改变状态的轮次，是把时间塑形奖励解释为努力的前提。

### A.3 奖励形状比较

在各塑形变体中，linear、Gaussian 和 step 的总体表现相当，说明只要存在明确计时信号，时间奖励的精确形状影响不大。主要差异在预算匹配：step 奖励产生最可靠的遵守，因为超过预算后它完全不给模型奖励。奖励形状及其行为的更详细比较见原文附录表 10。

### A.4 MLE-Bench 上的动作时长

在 MLE-Bench 上，动作时长具有随机性，并依赖 Agent 无法控制的因素（GPU 可用性、数据加载、网络延迟）。同一训练脚本可能因系统负载耗时 30 秒或 3 分钟。这使奖励带有与 Agent 决策无关的噪声，增加 RL 中的信用分配难度 [9]。仅运行框架条件已经达到 99.7% 的预算利用率，留给 RL 的改善空间很小；动作时长方差可能解释了为什么 MLE-Bench 上的 RL 训练相对未训练框架几乎没有增益。

## 摘要

随着大语言模型（LLM）越来越多地处理复杂推理任务，测试时扩展（test-time scaling）已成为增强能力的关键。然而，在频繁调用工具的 Agent 场景中，传统的“按生成长度定义”的测试时扩展失效了：工具延迟使推理时间与生成长度解耦。我们提出 **Timely Machine**，把测试时重新定义为墙钟时间，模型据此根据时间预算动态调整策略。我们提出 **Timely-Eval** 基准，覆盖高频工具调用、低频工具调用和时间受限推理。通过改变工具延迟，我们发现：较小模型在快速反馈下通过更多交互而表现更好，较大模型则凭借更高的交互质量在高延迟设置中占优。此外，现有模型无法让推理适应时间预算。为填补这一缺口，我们提出 **Timely-RL**：在冷启动监督微调之后，用强化学习增强时间规划。Timely-RL 提升了时间预算意识，并在 Timely-Eval 上持续提高性能。我们希望这项工作为 Agent 时代的测试时扩展提供新视角。

## 1 引言

随着大语言模型（LLM）的参数规模和数据规模持续扩大，仅靠扩展这些维度正变得越来越昂贵。以 OpenAI-o1 和 DeepSeek-R1 为代表的新一波模型转向探索**测试时扩展**，即分配更多推理时间来处理复杂推理任务 [7,12]。受 Group Relative Policy Optimization（GRPO）启发，基于可验证奖励的强化学习（RLVR）方法已成为增强 LLM 推理的主流范式 [24,11,36]。

此外，很大一部分研究把 RLVR 应用于涉及外部工具和环境交互的场景 [20,16]。借助 LLM 的推理能力，面向交互任务的 Agent 系统——例如网页搜索和自动化机器学习模型训练——也展现出巨大的应用潜力 [13,14]。

就 LLM 的推理能力而言，测试时扩展是一个关键概念。在 LLM 广泛应用于工具使用场景之前，标准推理任务（如数学、代码和常识推理）中的测试时扩展通常与生成时间相关 [19,33,8]。直观上，在只涉及模型推理的场景中，时间与生成长度之间存在内在正相关。

然而，当讨论以复杂工具使用为特征的 Agent 场景时，这种关系不再成立。在这类设置中，工具执行延迟不可预测，因此完成任务所需的总时间不能仅根据模型的生成长度估计。一条简洁的推理轨迹如果调用高延迟工具，可能消耗大量时间；反过来，在快速环境反馈下，更长的轨迹甚至可能更快结束。因此，传统基于生成长度的测试时扩展定义不适用于 Agent 任务。Liu 等人 [18] 通过外部插件为模型提供剩余工具调用预算。该方法有效，但等价于把预算当作工具调用次数，仍然忽略了工具本身的延迟。

在本工作中，我们引入 **Timely Machine** 概念。通过将测试时间与生成 token 解耦，我们恢复了“测试时间”作为物理量的原始含义：**时间本身**。我们认为，对任务时长有感知、以及为任务成本做规划的能力，应当是 LLM 的内在能力。

具体而言，当环境反馈具有高延迟时，模型应调整交互频率，并优先保证每一轮交互的质量，以取得更好结果；反过来，当环境响应迅速时，模型应更快地交互，收集更充分的反馈，从而在相同时长内探索更高收益。

为验证这一能力，我们提出 Timely-Eval，一个用于评估模型如何根据时间反馈调整策略的基准。Timely-Eval 精心设计了三种不同的交互场景：高频工具、低频工具和严格时间约束下的通用推理。通过这些任务，我们评估模型是否意识到“时间”概念，以及能否利用这种意识动态调整推理策略。

随后，我们通过调节反馈延迟，评估模型在不同工具延迟设置下的表现。我们发现：在工具延迟较短的任务上，相对较小的模型有时由于能进行更多轮交互而取得比大模型更好的表现；但随着交互时间增加，小模型的速度优势逐渐减弱，而大模型凭借更高的交互质量往往获得更大回报。

为了进一步训练模型具备准确的时间意识，我们首先合成一个大型 Timely Reasoning 数据集，其中每个样本都严格遵循任务完成的时间约束。然后，我们用该数据集对基础模型进行监督微调（SFT），得到具有时间意识的初始模型；再在这些初始点上提出 Timely-RL 做进一步增强。作为 GRPO 的变体，Timely-RL 鼓励模型最大化利用给定的时间预算。经过 Timely-RL 训练后，模型展现出有效规划和利用时间预算的能力。

总结而言，我们的贡献如下：

1. 提出 Timely Machine，将 Agent 场景中的测试时重新定义为墙钟时间。
2. 提出 Timely-Eval，一个评估不同时间预算下推理能力的基准。
3. 通过评估发现：(i) 模型偏好随工具延迟变化——低延迟下较小模型通过更多交互胜过较大模型，高延迟下较大模型占优；(ii) 现有模型缺乏根据时间预算调整推理策略的能力。
4. 开发 Timely-RL，一种教模型进行时间感知推理的强化学习方法。Timely-RL 使模型形成准确的时间预算意识，并据此调整推理策略。

## 2 相关工作

### 2.1 LLM 推理的测试时扩展

在增强 LLM 推理的研究中，若干早期工作通过对多个回答投票来提高推理准确率 [31]。一些工作也探索了自我纠错的可能性 [37,23,10]。Yao 等人 [35] 提出思维树（Tree of Thought），把推理转化为按步骤分段的树结构。后来，一些研究将蒙特卡洛树搜索用于 LLM 采样，以处理更复杂的推理问题 [6,2]。

Shao 等人 [24] 提出 Group Reward Policy Optimization（GRPO）。GRPO 激发了一波通过可验证奖励强化学习（RLVR）增强模型推理的研究兴趣。在通用推理中，基于 RLVR 的后训练策略带来了显著性能提升 [11,25,29,34]。

随着 RLVR 在推理任务上取得成功，后续工作探索了涉及工具交互的 RL 实践 [20,5,27,15,16]。这些努力展示了把 LLM 通用推理能力应用到更复杂、Agent 化交互环境的潜力。

### 2.2 LLM 推理的预算控制

在 Agent 强化学习成为趋势之前，研究者已经研究了通用任务中的长推理链 [21,28,39]。在这些设置中，预算控制等价于控制输出长度。因此，一系列工作专注于调节生成长度 [19,33,8]，目标是让 LLM 对推理预算敏感并能动态调整。最近，一些研究通过额外设计把墙钟延迟纳入通用推理 [4,32]。转向 Agent 场景后，AgentTTS [30] 根据 FLOPs 分配任务预算，而 Liu 等人 [18] 引入外部插件来调节工具使用和推理预算。然而，这些方法都依赖额外设计。我们采取更激进的主张：**时间意识应当是模型的内在能力**。

## 3 预备研究

### 3.1 Agent 场景中的测试时扩展

在介绍方法之前，我们先澄清“测试时”的含义。在数学和代码等任务中，测试时等同于模型的推理时间。因此，对给定推理任务，假设模型执行 `N` 个推理步骤，总时间成本 `t_all` 可写为：

$$
t_{\mathrm{all}}=\sum_{i=1}^{N}t_{\mathrm{gen}}^{(i)}
\tag{1}
$$

其中 `t_gen^(i)` 表示第 `i` 步的生成时间。这里总时间等于推理时间，因此分配更大的时间预算等价于分配更大的 token 预算。然而，在带工具调用的 LLM Agent 任务中，总时间成本 `t_all` 变为：

$$
t_{\mathrm{all}}=\sum_{i=1}^{N}t_{\mathrm{gen}}^{(i)}+\sum_{i=1}^{N}t_{\mathrm{tool}}^{(i)}
\tag{2}
$$

其中 `t_tool^(i)` 表示第 `i` 步工具调用消耗的时间。由于工具延迟现在也是总体成本的一部分，测试时不再与生成 token 数直接成正比。为清晰起见，我们讨论以下三种情况。

#### 3.1.1 工具主导

先考虑每轮工具延迟远大于生成延迟的情况：

$$
t_{\mathrm{tool}}^{(i)}\gg t_{\mathrm{gen}}^{(i)}
\tag{3}
$$

此时生成时间对测试时影响很小。因此，在固定时间预算 `t_budget` 下，交互轮数 `N` 主要由工具延迟决定：

$$
N\approx\frac{t_{\mathrm{budget}}}{t_{\mathrm{tool}}}
\tag{4}
$$

因此，每轮交互质量成为决定任务表现的关键因素。对这类任务，模型应在每一轮更仔细地规划。

#### 3.1.2 模型主导

在某些场景中，工具延迟可忽略，模型甚至可以不使用任何工具就解决任务：

$$
t_{\mathrm{gen}}^{(i)}\gg t_{\mathrm{tool}}^{(i)}
\tag{5}
$$

此时测试时又回到传统设置，总成本由生成 token 数主导。

#### 3.1.3 二者相当

在更一般的设置中，模型生成延迟和工具调用延迟往往处于相似量级，即：

$$
t_{\mathrm{tool}}^{(i)}\approx t_{\mathrm{gen}}^{(i)}
\tag{6}
$$

在这一区间，测试时计算由工具延迟和生成延迟共同决定。我们定义每步延迟比为：

$$
m_i=\frac{t_{\mathrm{tool}}^{(i)}}{t_{\mathrm{gen}}^{(i)}}
\tag{7}
$$

于是 `t_tool^(i)=m_i t_gen^(i)`，总成本变为：

$$
t_{\mathrm{all}}=\sum_{i=1}^{N}(m_i+1)t_{\mathrm{gen}}^{(i)}
\tag{8}
$$

由于 `t_gen^(i)` 和 `t_tool^(i)` 事先都未知，`m_i` 可能在步与步之间大幅变化。当 `m_i>1` 时，工具延迟主导，模型应花更多精力提升每次工具调用的质量；当 `m_i<1` 时，生成主导，模型可缩短推理以支持更多交互轮次。总体而言，由于 `m_i` 不可预测，基于 token 的预算控制并不充分。因此，Agent 系统必须让策略以时间为条件，并根据观察到的延迟反馈动态适应。

## 4 方法

本节介绍引言中提出的 Timely-Eval 和 Timely-RL。

### 4.1 Timely-Eval

为衡量 LLM 的时间意识及其在 Agent 任务中调节行为的能力，我们提出 Timely-Eval，覆盖三类任务：(i) 交互式文本游戏；(ii) 机器学习任务；(iii) 通用推理任务。

#### 4.1.1 交互式游戏

交互式小说游戏为 Agent 扩展提供了自然的测试平台。我们基于 Jericho——一个把 Agent 连接到 Zork 等经典文本游戏的接口——构建环境。在这些环境中，模型通过多轮交互导航，选择动作以最大化奖励。

由于这些游戏很轻量，我们可以轻松为每个动作指定任意的交互延迟，而不必担心实际工具执行时间。这使我们能够模拟高延迟和低延迟场景，从而探索模型如何在不同的时间约束下调整策略。我们对每个模型做基准测试，得到其平均每步延迟 `τ`，然后把时间预算设为 `τ` 的整数倍。

#### 4.1.2 机器学习

在机器学习任务中，工具执行主导时间预算。我们改编 MLEBench-Lite [1] 中的若干任务：LLM 应训练 ML 模型来解决给定问题。模型应与代码解释器交互，在多次迭代中提交解、观察执行输出、错误信息和性能分数。

估计平均每轮延迟 `τ`（包括 LLM 推理和模型训练）后，我们分配 `τ` 的若干倍作为时间预算。由于 ML 模型训练通常耗时，这一套件评估 LLM 在工具成本主导时能否有效利用额外时间预算。

#### 4.1.3 通用推理

最后，我们回到标准推理任务，其中测试时等价于生成时间。为确保模型依据时间（而不只是 token 长度）做条件推理，我们提供一个报告已用时间的计时器工具。模型必须在推理过程中查询它以避免超时。和前面一样，我们运行速度测试得到 `τ`，并把每个实例的预算设为缩放倍数。该套件检验时间意识是否能自然涌现。

### 4.2 Timely Cold Start（时间化冷启动）

在应用强化学习之前，我们首先蒸馏监督数据，以提供冷启动并建立基线。

在通用推理任务上，我们从 AM-DeepSeek-R1-Distilled-1.4M [40] 中采样查询，并从 Qwen3-235B-2507-Instruct [34] 蒸馏 100 万个训练样本。具体而言，我们给教师模型配备计时器工具，使其能在不同时间预算下生成解。

类似地，我们在交互游戏上从 DeepSeek-V3.2 [17] 蒸馏交互轨迹。为防止记忆化，我们把蒸馏限制在每个游戏的前 50 步，确保后续探索必须被学习，而不是简单回忆。我们不为 ML 任务做任务特定蒸馏。

蒸馏后，我们将合成数据与 DataScience-Instruct-500K [38] 结合，形成最终冷启动混合数据。通过对不同基础模型做 SFT，我们为后续 RL 训练提供初始化点。

### 4.3 Timely-RL

工具延迟产生动态、实时的反馈信号，天然适合强化学习。因此我们提出 Timely-RL，一种时间感知 RL 方法，训练模型在时间约束下优化行为。整体流程见图 1。

在第 `i` 轮交互中，时间反馈 `t^(i)` 由推理时间 `t_gen^(i)` 和工具执行时间 `t_tool^(i)` 相加得到。为使模型适应不同条件，我们把 `t_gen^(i)` 乘以系数 `α` 作为模型收到的反馈，以模拟更快或更慢的设备。

接下来，我们为三类任务设计 RL 训练奖励。对每个回答，令 `r` 表示正确性奖励，`t` 表示任务完成的时间成本，`T_max` 为时间限制。奖励函数可写为：

$$
R(t,r)=
\begin{cases}
0, & t>T_{\max},\\
r_{\mathrm{f}}, & t\le T_{\max},\ r=0,\\
r_{\mathrm{f}}+r+\lambda U(t), & t\le T_{\max},\ r>0,
\end{cases}
\tag{9}
$$

其中 `r_f` 是正确格式并及时完成的固定奖励，`U(t)` 表示模型对时间成本的利用率：

$$
U(t)=\sin\left(\frac{\pi}{2}\cdot\min\left(\frac{t}{T_{\max}},1\right)\right)
\tag{10}
$$

这确保时间比例接近 1.0 时奖励增长变慢，避免截止时间附近微小的时间差异造成大幅奖励波动。

### 5.2 实验设置

#### 5.2.1 Timely-Eval 细节

我们先介绍 Timely-Eval 的组成。对于交互游戏，我们从 Jericho 环境收集并封装了 57 个基于文本的交互游戏。模型可使用工具执行动作、查询合法动作、查看分数和终止游戏。

通用基准包含三个推理基准：AIME、MATH 和 GPQA-diamond [9,22]。模型获得一个跟踪已用推理时间的工具，必须根据时间成本和预算消耗调整推理策略。

ML 基准包含四个 ML 任务：Leaf Classification、Spaceship Titanic、Random Acts of Pizza 和 Detecting Insults in Social Commentary。模型可以使用工具执行代码、获得结果并监控已用时间。

#### 5.2.2 评估设置

接着介绍 Timely-Eval 的实验设置。对通用基准，我们把时间预算设为一个基线的 0.75×、1.0×、2.0× 和 3.0×；超过预算的回答视为错误。我们报告跨预算的平均准确率。

对机器学习基准，我们测量每个推理步骤（包括工具调用）的平均时间，并分配该时长的 1× 到 5× 作为预算。

对交互游戏，我们为不同工具分配延迟以模拟真实执行。我们在四个游戏（Enchanter、Zork1、Advent、Detective）上评估，预算分别等价于 30、50、100 和 200 步，报告跨设置的平均分数。5.1 节中预算范围为 30 步到 400 步以上。

#### 5.2.3 训练设置

我们先进行 SFT 冷启动，然后执行 Timely-RL。SFT 使用 Xtuner [3] 训练 2 个 epoch。对 RL，每个样本 rollout 8 次，批大小为 16，最大生成长度为 16,384 个 token。学习率设为 1e-6，裁剪比率为 [0.2,0.28]。RL 使用 VeRL [26]。

### 5.4 训练 LLM 做到“按时”

我们进一步设计实验，验证 Timely-RL 是否真的赋予模型更好的时间意识。

**图注：图 4** ML 任务和交互游戏上的扩展实验。

#### 5.4.1 缩减预算下的行为

为展示这一点，我们先选择通用基准，比较不同模型在 0.75× 时间预算下的按时完成率。如表 2 所示，以 Qwen3-8B 为代表的模型无法适应更短的时间约束，因而无法在时限内完成推理。然而，TimelyLM-8B 能利用计时工具实时获取剩余预算，并在各项任务中调整推理过程，从而使更多任务按时完成。

此外，我们观察到两个有趣现象。第一，预算缩减造成的性能变化在不同基准上不同。在 AIME 和 GPQA-diamond 等更难任务上，更高的完成率并未让 TimelyLM 显著超过其他模型。但在 MATH 等更简单问题上，模型的按时完成率与其准确率更接近，这意味着大多数按时完成的任务都正确解决了。在此类任务上，按时完成的收益超过进行更广泛推理的收益。

第二，比较更强的模型，DeepSeek-V3.2 更好地利用工具调用获取剩余时间，而 GPT-5.1 更偏好单轮推理以满足时间约束。Qwen3-8B 与 Qwen3-32B 之间也出现类似模式：32B 偏好单轮推理后直接总结，8B 更愿意在总结前调用工具。14B 模型几乎完全忽略工具调用的指令要求，直接进行完整的单轮推理。

#### 5.4.2 增加预算下的行为

此外，图 3 展示了不同时间预算下推理长度的变化。我们观察到，随着时间预算增加，TimelyLM 的推理长度呈显著上升趋势。相比之下，Qwen 系列模型没有这种趋势，其推理长度在不同时间预算下仅小幅增加。这表明 Timely-RL 确实使模型学会根据变化的时间预算调整推理策略。

### 5.5 任务相关的预算敏感性

图 4 展示了提供额外时间预算对交互游戏和 ML 任务性能的影响。在 ML 任务上，我们观察到预算增加与性能提升之间几乎没有直接关系。前几轮生成的代码往往已经决定最终性能。相反，在交互游戏上，额外时间预算带来明显的分数提升。

因此，以机器学习为代表的任务更依赖生成质量。一旦解足够好，进一步测试时扩展的回报递减。相反，交互游戏需要多轮交互才能获得奖励。对这类探索型任务，持续测试时扩展的收益仍然明显。

## 6 结论

本工作提出 Timely Machine 概念，主张 Agent 场景中的测试时应直接对应物理时间本身。我们倡导 LLM 应具备时间预算意识。为此，我们提出 Timely-RL，训练模型更好地感知任务执行时间并据此动态调整推理。我们希望这项工作为 Agent 场景中的测试时扩展提供新视角。

## 局限性

最后讨论本工作的若干局限。第一，我们的评估目前基于文本任务。在多模态交互任务中，处理图像或视频流通常会引入更复杂、更多变的延迟，是更具挑战性的场景。第二，我们的框架尚未充分处理 LLM 部署在多 Agent 系统中的情况。在这种多 Agent 设置中，延迟可能来自另一个 LLM 的生成时间，训练 LLM 在此类情境下有效协作仍是开放问题。最后，一个有趣观察是：虽然模型在时间约束下变得更按时，但准确率提升因基准难度而异。未来工作可以探索如何更好地平衡时间约束与模型性能之间的取舍。

### A.1 Timely-Eval 实现细节

#### A.1.1 通用基准

在 Qwen3 系列模型评估中，所有实验均在配备 8×NVIDIA H200 GPU 的硬件上一致进行。为确定每个基准的时间约束，我们先在无任何时间限制下对每个用例执行一次基线推理；然后用该基线时长乘以指定系数，得到目标时间限制。

#### A.1.2 交互游戏

交互游戏任务基于 Jericho 框架构建，支持 57 个交互式小说游戏。模型获得环境初始观察，并被要求尽可能获得更多分数。训练划分具体包含 16 个游戏：`acorncourt, advent, adventureland, anchor, awaken, balances, ballyhoo, curses, cutthroat, deephome, detective, dragon, enchanter, hhgg, hollywood, zork1`。

模型通过以下工具与引擎交互：

- `step(action)`：执行游戏动作。
- `get_available_actions()`：获取合法动作。
- `get_score()`：查看当前分数。
- `get_max_score()`：查看目标分数。
- `end_game()`：终止会话。

#### A.1.3 机器学习任务

Timely-Eval 的第三个组成部分是四个代表性 ML 任务：`leaf_classification`、`spaceship_titanic`、`random_acts_of_pizza` 和 `detecting_insults_in_social_commentary`。模型需要完成端到端数据科学推理，包括数据预处理、模型选择、训练和评估。每轮中，模型生成实现计划和对应 Python 代码；代码通过专用工具 `execute_code_and_get_duration(code)` 执行，该工具返回执行 stdout、最终评估准确率和消耗时间。

#### A.1.4 推理与评估设置

评估阶段，所有模型部署在配备 8×NVIDIA H200 GPU 的硬件集群上。为高吞吐推理，采用 SGLang 框架 [41]。为平衡效率与稳定性，所有基准的模型调用并发度（并行请求数）设为 16。对存在固有方差的任务——特别是交互游戏和机器学习任务——每个用例独立评估 8 次；报告结果为这些迭代的汇总表现，以保证统计显著性并降低随机生成的影响。

#### A.1.5 时间预算分配策略

对通用任务，时间预算按用例确定。令 `x` 表示模型在无时间约束的基线推理中完成某个用例所需的时长，则对该用例强制的时间预算定义为 `n×x`，其中 `n` 是可配置的缩放因子。这样做能自然地将每个问题的内在难度纳入考虑。

对交互游戏和机器学习任务，我们采用基于步骤的预算策略：总时间预算等于测得的平均每步时长（来自基线表现）乘以一个固定常数。这样可在多轮交互或完整编码流程中，对模型的策略规划和工具调用效率保持一致压力。

### A.2 Timely-RL 实现细节

RL 框架基于 VeRL [26] 和 InternBootCamp。我们为三类任务设计了相应的工具和 RL 流程。统一奖励函数重述如下：

$$
R(t,r)=
\begin{cases}
0, & t>T_{\max},\\
r_{\mathrm{f}}, & t\le T_{\max},\ r=0,\\
r_{\mathrm{f}}+r+\lambda U(t), & t\le T_{\max},\ r>0,
\end{cases}
\tag{11}
$$

$$
U(t)=\sin\left(\frac{\pi}{2}\cdot\min\left(\frac{t}{T_{\max}},1\right)\right)
\tag{12}
$$

其中 `r_f` 是正确格式并及时完成的固定奖励，`U(t)` 是时间利用率。

#### A.2.1 计时器工具

我们实现了只支持一个函数调用的 Timer Tool：`get_duration()`。为模拟多样执行环境，工具初始化可设置特定时间缩放系数和随机扰动因子（jitter）。当模型调用该工具时，返回时长等于实际已用时间乘以指定系数，再加上随机噪声。该设计使 Timely-RL 能泛化到不同计算资源和推理速度。

#### A.2.2 通用推理 RL

对通用推理任务，Timer Tool 是时间意识的主要接口。我们部署专门服务管理不同用例的计时器。每次 VeRL rollout 会话前，每个用例都在该服务注册，确保各实例计时严格独立且隔离。

RL 过程中，鼓励模型调用 `get_duration()` 监控自身推理进度。按式（11）的奖励，对通用推理任务设置：任务奖励 `r=0.5`（答对时），格式奖励 `r_f=0.1`，时间利用权重 `λ=0.4`。

#### A.2.3 交互游戏 RL

对交互游戏任务，我们部署专门服务托管 Jericho 游戏引擎。每个 rollout 会话前初始化一个隔离游戏实例。模型调用指定工具与环境交互，直到游戏到达终止状态或模型显式调用 `end_game`。我们把 Timer Tool 直接集成到该服务中，确保模型在同一轮同时获得环境反馈和总已用时间。

关键是，我们区分推理时间（模型生成延迟）和工具调用时间（环境执行延迟，包括模拟工具延迟）。为模拟不同推理速度，我们对实际推理时间施加缩放系数，而工具调用时长保持不变。这种分离使我们可以更好地分析模型在不同计算约束下的策略行为。对交互游戏，`r` 计算为：

$$
r=\left(\frac{s_{\mathrm{curr}}}{s_{\max}}\right)^{1/3}
\tag{13}
$$

其中 `s_curr` 是该局获得的分数，`s_max` 是游戏最高分。

#### A.2.4 机器学习任务 RL

最后，对机器学习任务，我们部署专门代码执行服务处理模型生成的脚本。与交互游戏不同，ML 任务不需要维护复杂的环境状态转移；因此我们只需为每个用例实例化单独的 Timer Tool 来监控执行时长。

在此类别中，式（11）中的性能分量 `r` 对应模型代码在测试集上取得的评估指标（准确率）。由于四个 ML 基准都是分类任务，`r` 自然是 [0,1] 范围内的浮点数。为平衡总奖励量级，我们把性能对最终奖励的贡献定义为 `0.5×r`。

### A.3 提示词与游戏初始观察

原文附录为四个 ML 基准分别设计了任务提示词，并提供了代表性 Jericho 游戏的初始观察与提示词；每个任务给模型一个 `max_score` 目标以及起始环境的文本描述。由于这些提示词是训练和评估协议的一部分，本译文保留其原文，具体见原文附录 A.3、A.4。

### B. 蒸馏细节

为给 Timely-RL 提供高质量冷启动基础，我们开发了蒸馏流程，使用从 AM-1.4M 数据集采样的查询。教师模型为 Qwen3-235B-Instruct-2507，配备 Timer Tool，并被要求在严格执行的截止时间内准确完成任务。为确保模型泛化到各种硬件场景和推理速度，数据合成时随机采样不同时间限制和计时器加速系数。

## 摘要

LLM Agent 被部署在必须通过交互获取信息的环境中。在这些场景里，Agent 必须对行动方式中固有的“成本—不确定性”权衡进行推理，例如何时应停止探索并提交答案。举例来说，在编程任务中，Agent 可以运行自己生成的代码，也可以为这段代码生成测试；编写和运行测试的成本非零，但通常低于运行有 bug 代码的成本。在本工作中，我们表明可以引导 LLM Agent 显式推理如何平衡这些成本—不确定性权衡，从而在环境中更优地行动。我们把多个任务形式化为不确定性下的序贯决策问题，包括检索增强问答和文件读取编程任务。每个问题都有影响 Agent 表现的潜在环境状态。我们提出一个名为 **Calibrate-Then-Act（CTA）** 的框架：向 Agent 传入关于该环境状态的推断先验，使其能更优地行动。这些信息会定性地改变 Agent 行为，并赋予 Agent 一种无法通过标准 RL 训练学到的环境敏感性。我们在合成任务、QA 和文件读取任务上的结果表明，用 CTA 把成本—收益权衡显式化，有助于 Agent 发现更优的决策策略。

## 1 引言

**图注：图 1** 给定同一任务，编程 Agent 可以选择仔细地通过中间检查验证假设（右），也可以尽快尝试直接给出解（左）。最优选择取决于不确定性和具体成本约束。Calibrate-Then-Act（CTA）把这类信息显式化，以支持更好的决策。

大语言模型（LLM）Agent 正越来越多地承担信息不完整环境中的任务。理性行为要求通过探索环境来获取信息。然而，探索是有成本的：每多一步都会增加 API 成本、交互延迟和用户负担。

这种探索及其成本有多种形式。在软件开发和调试中，Agent 必须决定是先运行有针对性的检查，还是直接执行完整程序后再提交解 [68]。在机器学习实验中，实践者要在有限计算预算下权衡廉价的代理评估与昂贵的完整训练 [28,24,60]。在诊断和科学发现中，额外测试或实验会降低不确定性，但会产生金钱、时间或安全成本 [29,33,21]。购物 [61,55]、推荐 [25] 和工具增强问答 [63] 等在线决策场景也呈现相同结构：Agent 要权衡继续收集信息与凭部分信息行动。

Agent 的探索策略会以复杂方式依赖提示词、输入和训练数据。然而，这些策略往往是静态的。例如，ChatGPT Deep Research 总是在搜索前只问一轮澄清问题 [12]；SWE-agent [62] 等编程 Agent 会先通读现有代码库。这与图 1 形成对比：如果模型确信自己理解了问题设置，并能恰当地权衡探索与行动成本，它就可以更高效地行动。

在本工作中，我们问：**如何开发能在不同成本和不确定性剖面下以最优方式探索的 LLM？** 借助现代 LLM 强大的推理能力，我们提出 Calibrate-Then-Act（CTA）框架，把不确定性的校准与动作选择的推理解耦。关键洞见是：通过向模型显式呈现先验，我们引导模型抽象地推理潜在的序贯决策问题，并发现最优动作。

我们研究两个受现实问题启发的设置：(1) 可选检索的知识问答，其中不确定性从模型自身置信度推断；(2) 编程任务，其中关于环境结构的先验（如文件格式模式）来自过去经验学到的线索。我们表明，即使在这些简单设置中，通过提示或 RL 训练的 LLM Agent 也无法达到最优行为。然而，这并不是因为它们无法进行正确推理：在一个合成“潘多拉魔盒”问题 [56] 上，我们表明即使小型思考模型（Qwen3-8B）也能遵循最优策略。Calibrate-Then-Act 方法建立在这一结果之上，向 Agent 提供由模型置信度估计或训练好的环境状态预测器确定的相关环境信息。该方法的零样本提示实现 CTA-Prompted 已经能够进行动态决策。我们表明，用 RL 进一步训练可提升性能，并显著优于对 Agent 做基线 RL 训练。

我们的贡献是：(1) 将环境探索框定为序贯决策问题，并在三个设置中统一；(2) 提出 Calibrate-Then-Act 方法，引导 LLM 推理其动作的最优性，并取得比基线更好的成本—性能权衡。

## 2 背景：带成本的 Agent 探索

我们把成本感知的环境探索任务形式化为序贯决策问题。Agent 在本工作中是一个 LLM，给定查询 `x`，并在某个环境中行动。该环境可定义为部分可观测马尔可夫决策过程：

$$
\mathcal{W}=(\mathcal{S},\mathcal{A},\mathcal{O},O,T,R,D_{\theta})
$$

它是状态 `S`、动作 `A`、观察 `O`、观察函数 `O`、转移函数 `T`、奖励函数 `R` 和参数化折扣函数 `D_θ` 的元组，其中折扣函数整合了成本。

在我们考虑的设置中，`A` 和 `O` 都是字符串值空间；LLM 产生字符串动作（代码、API 调用等），并接收环境的字符串响应。观察函数 `O` 产生底层环境的字符串实现；例如在图 1 中，执行命令的结果以终端字符串输出的形式返回，反映底层环境状态。

环境包含决定 Agent 表现、但无法直接观测的关键特征，例如图 1 中未观测文件的格式细节。这些特征可视为 `S` 中信息的一个子集。我们用随机变量 `Z` 表示，取值 `z ∈ Z`。

Agent 在多个时间步与环境交互，然后终止。在每个时间步 `t`，Agent 选择动作 `a_t ∈ A` 并收到观察 `o_t ∈ O`；为简单起见，假设 `o_t` 编码了 `a_t`。基于这些信息，可形成理想后验分布 `b_t(Z)=p(Z|x,o_{0:t})`，它反映关于潜在变量的剩余不确定性。动作空间通常包含多个探索动作和一个提交动作，后者通过产生最终结果终止 episode。在图 1 中，探索动作包括查询输入数据文件的某些方面；其他动作（图中未显示）包括运行代码、编写并运行单元测试。

每个动作根据不同设置产生不同成本，而提交动作对应返回最终解。这些成本由折扣因子 `D_θ(a_{1:T}) ∈ [0,1]` 反映，它根据提交前采取的探索动作对成功完成任务的价值打折。最后，Agent 在提交时获得奖励：

$$
R=\mathbb{I}[\text{task completed at }a_t]\cdot D_{\theta}(a_{1:T})
$$

总体而言，Agent 的目标是通过仔细选择动作，响应环境的不确定性和成本约束，自适应地平衡探索与提交，从而最大化期望折扣奖励 `R`。

### 3.1 潘多拉魔盒：成本感知决策的最小设置

#### 形式化

我们考虑经典潘多拉魔盒问题的一个变体，奖励随时间折扣 [56]。任务涉及有限 `K` 个盒子 `{z1,z2,…,zK}`，其中恰好一个盒子 `z*` 含有价值为 1 的奖品。该盒子对 Agent 未知，并从先验分布中抽取：

$$
p(z_k=z^*)=p_k,\quad \sum_{k=1}^{K}p_k=1
$$

在每个时间步 `t`，Agent 可以选择验证一个盒子 `z_{k_t}` 看它是否含奖品，并按 `γ ∈ [0,1]` 折扣最终奖励；也可以根据当前信息提交一个盒子，获得奖励：

$$
R=\gamma^t\cdot\mathbb{I}(z_{k_t}=z^*)
$$

该任务可看作 LLM Agent 现实用例的玩具版本。例如，在尝试识别代码中的 bug 时，可以把“提交”看作直接采取行动修复 bug，把“验证”看作编写单元测试检查代码正确性。

要最优行动，必须知道先验概率。最优策略是：如果某个盒子的后验概率大于 `γ`，就提交该盒子，因为此时猜测的期望价值高于继续验证；否则，最优决策是验证剩余盒子中概率最高者。完整算法见算法 1，证明见附录 H。

### 3.2 QA 任务：可选检索的知识问答

我们研究一种知识问答设置，其中 LLM 可以可选地以一定成本获取外部信息 [15]。给定事实性问题，模型必须决定是依赖参数化知识，还是推迟提交并检索额外证据，在潜在准确率收益与延迟和 API 成本之间权衡。

#### 形式化

给定问题 `x`、折扣因子 `γ ∈ [0,1]` 以及对检索器的访问，Agent 在动作 `A={retrieve, answer}` 之间选择。`retrieve` 用输入 `x` 查询检索系统；`answer` 调用 LLM 在迄今上下文下回答问题，产生答案 `a`。模型获得奖励：

$$
R=\gamma^t\cdot\mathbb{I}(a=a^*)
$$

其中 `a*` 是 `x` 的真实答案。该任务最多只有一轮检索，因此 `t` 为 0 或 1。

#### 潜在结构与先验

该问题有两个相关潜在变量。第一，定义 `p_da=p(a=a*|x)` 为模型在不检索、直接作答时答对的概率。我们用分布 `p(p_da|x)=δ(z=k(x))` 建模 `p_da`，其中 `k_da(x)` 是 LLM 返回正确答案的估计，`δ` 是狄拉克 delta 函数。该分布表示我们对模型答对概率有一个点估计。

第二，定义检索后答对概率 `p_ret=p(a'=a*|x,c)`，其中 `c` 是检索到的上下文。我们同样用 delta 函数表示：`p(p_ret|x)=δ(z=k_ret)`。

在这一抽象下，只要检索后的期望折扣准确率超过直接作答，神谕策略就会检索：

$$
p_{\mathrm{ret}}\cdot\gamma\;\ge\;p_{\mathrm{da}}
$$

### 3.3 FileReading 任务：带选择性测试的编程

参照图 1，我们设计一个编程设置，以概括“模型选择直接运行代码还是先测试代码”的思想。具体而言，模型需要编写代码，以正确的格式选项加载数据文件，并返回任务查询的答案（例如找出最高分对应的 user_id）。输入没有说明真实文件模式；模型只能从文件名线索和过去经验推断可能格式。与 QA 设置不同，这些先验并非模型事先已知，而必须通过在该任务上训练来学习。尽管设置简单，我们表明 LLM Agent 通过 RL 仍无法学到最优行为。

#### 形式化

给定包含任务说明和 CSV 文件名 `n` 的查询 `x`，Agent 需要编写代码正确加载文件并计算答案 `a`。具体而言，每个文件关联潜在格式属性：

$$
\mathbf{z}=(z_d,z_q,z_s)\in\mathcal{Z}
$$

其中 `z_d ∈ {, ; \t}` 表示分隔符，`z_q ∈ {' "}` 表示引号字符，`z_s ∈ {0,1}` 表示跳过表头的行数。若不能正确推断 `z`，任务无法解决。

在每个时间步 `t`，Agent 从三类动作中选择一个：`UNIT_TEST(f)`、`CODE(d,q,s)` 或 `ANSWER`。

- `UNIT_TEST` 探查选定的格式属性 `f`，揭示其真实值。
- `CODE` 执行按 Agent 当前信念 `(d,q,s)` 编写的代码，通过 stdout 和 stderr 返回反馈，其中可能包含答案或有助于调试和改进的信号。
- `ANSWER` 提交最终答案 `a'` 并终止 episode。

Agent 可以按任意顺序交错执行 `UNIT_TEST` 和 `CODE`，也可以基于之前的执行反馈执行多次 `CODE` 来改进解。每个 `UNIT_TEST` 和 `CODE` 动作分别产生乘性折扣 `d_u` 和 `d_c`。在时刻 `T` 通过 `ANSWER` 提交时，Agent 获得奖励：

$$
R=d_u^U\cdot d_c^C\cdot\mathbb{I}(a'=a^*)
$$

其中 `a*` 是真实答案。

#### 先验

格式属性上的先验分布 `p(z|n)` 可从惯例、过去经验推断，或由格式预测器显式提供。这些任务的提示词模板见附录 J。

## 4 方法：校准 Agent 的环境探索

**图注：图 2** 标准 Agent 决策循环（左）与本文方法 CTA（右）。在 CTA 中，我们从训练数据学习先验估计器，并在推理和/或训练时让 Agent 以估计的 `p̂` 为条件，通过显式推理先验概率来诱导更优决策。

要在序贯决策问题中达到帕累托最优，Agent 必须联合比较额外探索的成本与额外信息的期望价值，以决定是继续探索还是基于当前部分信息提交。额外信息的价值取决于通过先验 `p(z|x)` 和后验 `b_t` 对当前世界状态信念的推理。

我们将 LLM Agent 定义为 `π(a_t|x,A,D_θ(·),o_{0:t})`，它给出给定状态下下一动作的分布。图 2 左侧展示该 Agent 的基本形式。`π` 可以通过提示 LLM 或通过强化学习训练模型来实现。然而在实践中，`π` 很难在我们评估的环境中学会正确推理。

我们的关键方法贡献是显式提供先验估计，记为 `p̂(Z|x)`。图 2 右侧展示先验估计在 Agent 决策循环中的作用。我们实现该方法的两个版本：

- **CTA-Prompted**：使用与基线相同的 Agent `π`，但修改提示词，把先验信息 `p̂(Z|x)` 与 `x` 一起加入。提示词示例见附录 J。
- **CTA-RL**：使用 CTA-Prompted 的提示词，并进一步用 RL 训练。我们使用 GRPO [47] 和任务本身的折扣奖励目标，对模型做端到端微调。评估时在新样本上使用与训练时相同的提示词。

两个设置都依赖思考型 LLM 判断如何使用这些信息。6.1 节表明，在给定适当先验时，思考模型可以解决潘多拉魔盒问题；6.2 节和图 3 进一步表明，思考模型在关注的任务上也表现显著更好。

准确的先验估计对 CTA 成功很重要。下面描述如何估计表 1 中的先验。对潘多拉魔盒，先验是显式给出的；另两个问题需要估计，且需要两种不同估计方式。它们的共同点是：两种估计技术都抽取了难以通过端到端 RL 学到的推断，因此需要 CTA。

### 4.1 从模型置信度估计先验（QA）

在 QA 中，真实 `k_da(x)`（模型不检索即可答对 `x` 的概率）不可直接观测。这是一个置信度估计问题。有多种方法可得到模型置信度估计，包括检查 logits、基于探针的方法和口头化置信度。本工作使用口头化置信度 [40]，这是一种可同时适用于黑盒和玻璃盒模型使用的通用方法。给定问题 `x`，我们提示模型生成离散的口头化置信度值 `p_v(x)`，并应用在验证集上训练的同调回归模型 `ISO` [64] 得到校准估计：

$$
\hat{k}_{\mathrm{da}}(\mathbf{x})=\mathrm{ISO}\big(p_v(\mathbf{x})\big)
$$

在 PopQA 数据集 [38]（见第 5 节）上，该回归把期望校准误差（ECE）从 0.618 降到 0.029。这一下降反映了初始校准很差 [20,59,48,53]，也说明重缩放有帮助 [13]。这种重新校准很难通过端到端 RL 学到：如果在 QA 数据集上长时间做 RL，模型更可能记住具体事实，而不是系统性地重新校准自己的信念。

### 4.2 从训练数据估计先验（FileReading）

编程 Agent 在完成任务时会利用多种先验。我们的 FileReading 任务研究关于文件格式的推断，作为可控的代表性问题。设置中假设 Agent 在本任务上训练，因此基线 RL 和 CTA 方法都接触展示文件名到格式信息映射的数据。

对先验估计，我们训练一个文件名到格式的预测器 `M_BERT`，从文件名估计分布 `p(z|n)`。该预测器基于轻量 BERT-tiny 编码器（4.4M 参数）[5,51]。给定文件名 `n`，模型编码 token 化字符串，并用 `[CLS]` 表示通过三个线性头产生三个独立类别分布：分隔符、引号字符和跳过行数。模型在训练划分上训练一个 epoch，三个头使用交叉熵之和作为目标。在验证划分上，`M_BERT` 在三个格式属性上的平均分类准确率为 67%。这一准确率符合预期：真实格式值从一个依赖文件名的软先验中采样，最可能选项的平均概率约为 67%。因此，该任务被有意设计为随机可预测，而不是能从文件名确定性预测。附录 C 表明，预测器越差，CTA 表现越差，但退化是平滑的；有噪声的预测器仍然带来收益。

训练后，`M_BERT` 输出边缘概率 `{p(z_d|n),p(z_q|n),p(z_s|n)}`，在 RL 训练或测试时与每个任务一起提供给 Agent，从而把不确定性估计与动作选择解耦。

## 5 实验设置

#### 数据集

对 QA，我们在 PopQA [38] 上评估。这是一个覆盖长尾事实知识、适合检索增强的问答基准。我们采样 1,000 个问题用于评估，并基于 Contriever [26,3] 构建检索器。对每个问题，我们从均匀分布 `γ∼U[0.1,0.65]` 中采样一个折扣因子，以研究模型在不同检索成本下的行为。

我们的编程问题涉及一个基于 CSV 的问答数据集 FileReading。其中文件名线索为文件格式提供信息信号，正确解析需要用合适的格式值执行代码。测试时，真实文件格式隐藏，任务查询 `x` 中只提供文件名。FileReading 包含 2,000 个任务，划分为 1,400 个训练、300 个验证和 300 个测试样本。对每个任务，我们从 `[0.5,1]` 随机采样单元测试折扣 `d_u`，并在四种代码折扣设置 `d_c=d_u^ρ` 下复制实例，其中 `ρ∈{0.5,1.0,2.0,4.0}`，从而在保持任务固定的同时改变代码执行的相对成本。数据集构建细节见附录 G。

#### 指标

我们从三组指标评估模型表现。(1) 探索统计量：对 QA，报告检索率 Retrieve%（调用检索的问题比例）；对 FileReading，报告单元测试次数 `U` 和代码尝试次数 `C`。(2) 任务准确率，衡量最终模型输出是否与任务查询的真实答案一致。(3) 奖励，即用探索成本对正确性打折后的值。

#### 模型与基线

我们使用 Qwen3-8B [43] 作为 QA 和 FileReading 任务的基础模型。将以下基线与我们提出的 CTA-Prompted 和 CTA-RL 比较。

- **Prompted**：直接用任务描述和查询 `x` 提示基础模型。
- **Prompted-NonThink**：与 Prompted 类似，但通过在开头添加空 ` thinking</think>` 标签并去除思考内容来关闭思考模式。除非特别标注 `-NonThink`，其他所有设置默认启用思考模式。
- **RL**：使用 GRPO [47] 和折扣奖励目标对模型做端到端微调，评估时用任务描述和查询 `x` 提示。

为使两种 RL 设置都接触 FileReading 中多样的成本权衡，我们把每个训练实例在多个相对成本值 `ρ∈{0.5,1.0,2.0,4.0}` 下复制，因此 RL 训练集比训练 `M_BERT` 所用数据大 4 倍。更多训练细节见附录 I。

## 6 结果

### 6.2 Calibrate-Then-Act 让模型做出校准决策

#### 基线 LLM Agent 即使经过 RL 也难以做出校准决策

在 QA 和 FileReading 上，我们都发现：没有显式先验时，LLM 无法仅凭任务描述自然形成校准的决策规则。

对 QA，图 3 可视化了模型在不同检索折扣因子 `γ` 下的检索行为。每个堆叠柱展示某个折扣因子区间内模型的问题决策：红色表示回答前检索的样本比例，绿色表示直接回答。黑线报告神谕匹配率，即决策与最优“检索或不检索”规则（阈值 `k_da=γ·k_ret`）一致的比例。具体而言，Prompted-NonThink（图 3 左）在所有成本区间几乎总是检索，反映一种保守且对成本不敏感的策略。

启用思考模式减少了不必要的检索，但 Prompted（图 3 中）对检索成本适应很弱，神谕匹配率有限。Prompted 有时会定性推理自己的参数化知识，但很少把这些知识量化为用于期望值比较的确定性值；它有时提到成本，却没有稳定地把最终决策与成本联系起来。结果，其决策往往回退到基于回忆的启发式：想到可信候选就回答，否则检索，而不是系统性地适应 `γ` 和置信度。这表明，没有显式先验估计，模型难以评估自身参数化知识并做出一致的检索决策。

在 FileReading 上，图 4 展示类似分析。x 轴 `ρ=log d_c/log d_u` 反映相对成本：`ρ` 越大，代码尝试相对越昂贵，理性 Agent 理应在编码前做更多测试。每个堆叠柱表示具有特定 `ρ` 的任务集合，每种颜色表示该集合中动作轨迹模式的比例。柱上方标注奖励，并标注“先猜后干”（未做任何单元测试就尝试代码）的百分比。

Prompted 和 RL 都坍缩为静态的“先测试”策略，而不是跨成本区间适应，两者的“先代码”轨迹比例都很低。没有先验的 RL 无法内化训练数据结构，而是默认采用次优探索策略。综合来看，这些结果表明，当先验估计是隐式的时，LLM 难以做出校准、成本敏感的决策。

## 7 相关工作

#### 不完全信息下的决策

LLM 正越来越多地应用于信息不完整的任务，这些不完整来自用户查询表述不充分 [10,66,65,32,46]、歧义 [39,9,12] 以及部分可观测环境 [57,34,14,7,17]。为消除不确定性，模型常需要提出澄清问题 [44,23,31]、查询环境 [6,42,41] 或进行协作 [58,8]。以往工作通常关注训练或提示策略，而我们表明，当提供显式先验时，模型可以抽象推理最优解；我们利用这一点诱导此类推理。

#### 成本感知部署中的 Agent

基于 LLM 的 Agent 正越来越多地部署到需要多步推理和工具使用的现实场景，包括交互式编程 [50,68,54,27]、规划 [69,36]、问答 [63,15] 和科学研究 [45,22,30,1,2]。工具使用扩展了 Agent 的能力和可靠性，但与外部环境交互往往带来延迟 [18]、资源消耗 [11,37] 以及可能损害用户体验的开销 [16,25]。

为此，已有若干研究路线考察显式成本约束下的 Agent 行为。Liu 等人 [36] 提出以成本为中心的基准来评估 Agent 的工具规划能力。Wang 等人 [52]、Gul 等人 [19]、Wang 等人 [53]、Lin 等人 [35] 研究模型如何在保持答案质量的同时减少不必要的检索或工具使用，例如通过弃答、选择性搜索或效率导向的动作策略。Berant 等人 [4] 训练可适应成本系数的可操控澄清策略。效率探索中一个未被充分研究的方面，是联合处理不确定性先验和成本约束，因为二者共同决定帕累托最优决策。我们为交互式 Agent 任务提出统一框架，并表明校准先验是诱导 LLM Agent 进行适当决策的关键。

## 8 结论

本文提出一种让 LLM 在其环境交互中平衡不确定性—成本权衡的方法。通过向 LLM 提供关于环境中未观测特征的先验，LLM 能成功推理帕累托最优行为并有效应对动作成本。本工作展示了诱导 Agent 最优思考的新方式，并表明元层面信息（关于能力的先验）可能在塑造 Agent 策略方面发挥作用。

### A. 局限性

我们的实验聚焦受控的 QA 和 FileReading 设置，以隔离成本感知探索问题；但它们比具有更丰富动作空间、更长时域和更多噪声观察的开放式 Agent 部署更简单。我们使用这些设置来可靠评估决策质量；把 CTA 扩展到更复杂环境仍是未来有前景的方向。

CTA 还依赖可用且有价值的先验估计。敏感性分析表明，CTA 对中等估计误差具有鲁棒性，但当先验严重失准或自信地错误时，性能可能退化。我们展示了若干无需真实标签获取先验的方法，包括从模型置信度和历史任务数据获取；但为更广领域设计可靠先验估计器仍是未来工作。

最后，CTA 不保证在任意环境中达到最优行为。模型仍必须正确解释提供的先验，并推理其对动作选择的含义。在更复杂场景中，最优动作选择可能要求基础模型有更强推理能力，以处理后验更新、多步信息价值和多个潜在变量之间的依赖。

### B. 影响声明

本文提出一种广泛改善 LLM Agent 成本—收益权衡的方法。尽管它尚未集成到生产 Agent 系统中，我们设想该方法或其衍生方法未来可以集成，从而理想地降低成本并提高效率。与 LLM、Agent 和机器学习领域的其他进展相比，我们未预见该方法有特定弊端。潜在广泛弊端继承自 LLM 和 Agent 能力提升带来的弊端，例如进一步推动 AI 技术在社会中的传播。

### C. 对先验质量的敏感性

我们通过系统性地降低 CTA-RL 所用先验估计器的质量，评估 FileReading 任务中性能如何随先验质量变化。除基于 BERT 的学习先验外，我们构造了三种校准逐渐变差的替代先验：

- **Noisy（噪声）**：从 BERT 先验出发，随机选择 40% 的预测，交换正确选项和错误选项的概率。
- **Uniform（均匀）**：所有候选选项上的均匀分布，表示没有信息性先验知识。
- **Adversarial（对抗）**：交换正确和错误选项的概率，并把错误选项的概率抬高到 95% 置信度。

### E. 潘多拉魔盒问题的定性轨迹分析

我们展示三个设置的代表性交互轨迹：CTA-Prompted-NonThink、Prompted 和 CTA-Prompted。在关闭思考模式的 CTA-Prompted-NonThink（图 6）中，模型似乎没有比较额外信息的期望价值与探索成本。结果，它倾向于在提交前验证所有选项，而不考虑先验分布，造成不必要的探索。在 Prompted（图 7）中，模型无法访问先验概率。缺少校准的不确定性信息时，它实际上在隐式均匀先验下运行，因而遵循次优验证策略。

相反，在 CTA-Prompted（图 8）中，模型获得先验概率并启用思考模式。此时它会显式推理期望奖励与探索成本之间的权衡，比较立即提交的价值与继续验证的折扣价值。最终行为与神谕策略一致。

这些定性例子说明，显式先验信息如何诱导模型正确推理额外信息价值与动作成本之间的关系，并据此做出最优决策。

**图注：图 6** 3 个盒子的潘多拉魔盒交互轨迹示例，先验为 `(0.04,0.68,0.28)`，折扣因子 `γ=0.2`，关闭思考模式。在该设置中，模型在提交前探索所有盒子，并遵循次优验证顺序，而不是优先选择概率最高的选项。

**图注：图 7** 3 个盒子、先验 `(0.04,0.68,0.28)`、`γ=0.2` 的交互轨迹示例，模型未获得先验概率。在该设置中，模型隐式地把各盒子视为等概率，并遵循偏离最优策略的次优策略。

**图注：图 8** 3 个盒子、先验 `(0.04,0.68,0.28)`、`γ=0.2` 的模型推理轨迹示例。模型显式比较立即猜测与继续验证的期望价值，然后选择立即猜盒子 `B`，这是该情况下的最优策略。图中黄色高亮关键推理步骤，包括动作价值与探索成本的显式比较。该例说明，当先验被显式提供时，模型能够推理不确定性和探索成本，从而选择最优策略。

### G. 任务“带选择性测试的编程”的数据集构建细节

本附录描述神谕文件名到格式模型，以及生成编程任务数据集 FileReading 的流程。每个任务由结构化文件名、在潜在格式配置下生成的 CSV 文件和相关查询组成。

为捕捉文件名线索为文件格式提供信息信号的场景，我们构造带结构化文件名的 CSV 问答合成数据集。每个文件名由一小组指示性 token（如 `_eu`、`_tab`、`_sas`、`_cn`）与额外无关字符串组合而成。

我们定义神谕文件名到格式模型：

$$
\mathcal{M}_{\mathrm{oracle}}: n\mapsto p(\mathbf{z}\mid n)
$$

它把文件名 `n` 映射为格式配置 `z=(z_d,z_q,z_s)` 上的先验分布。例如，`_tsv` 这样的文件名 token 会显著提高制表符分隔符相对于默认逗号分隔符的概率。然后我们从 `p(z|n)` 采样真实格式配置 `z*`，并生成相应 CSV 内容和任务查询。

数据集构造保证：只有用完全正确的配置解析文件才能得到正确答案；错误的格式假设会导致解析失败或列错位。文件名用四个二元特征表示，因此共有 `2^4=16` 种不同文件名特征配置及其对应的格式属性先验分布。我们生成 2,000 个任务实例，每个包含文件名、按采样格式配置生成的 CSV 文件和相关查询；划分为 1,400 个训练、300 个验证和 300 个测试样本。

#### 潜在格式变量

每个任务实例关联一个潜在格式配置：

$$
\mathbf{z}=(z_d,z_q,z_s)
$$

其中 `z_d∈{`, `;`, `\t`}` 表示分隔符，`z_q∈{", '}` 表示引号字符，`z_s∈{0,1}` 表示跳过表头行数。当且仅当用完全正确的配置 `z*` 解析文件时，才能得到正确答案。

#### 文件名特征

我们从每个文件名 `n` 提取四个二元特征，分别表示特定子串是否出现：`has_eu`、`has_tsv`、`has_sas` 和 `has_cn`。每个特征取开或关，因此共有 `2^4=16` 种可能的文件名特征配置。每种配置对应由神谕模型诱导的、不同的格式属性先验分布。

#### 神谕文件名到格式模型

神谕模型把文件名 `n` 映射为格式配置 `z` 上的先验分布。对 16 种可能的文件名特征配置中的每一种，模型诱导对应格式属性先验。该先验分解为：

$$
p(\mathbf{z}\mid n)=[p(z_d\mid n),p(z_q\mid n),p(z_s\mid n)]
$$

其中每个因子都是文件名特征上的对数线性模型。

#### 采样与文件生成

对每个文件名 `n`，我们从神谕模型 `M_oracle` 采样格式配置 `z∼p(z|n)`，然后生成符合 `z` 的 CSV 文件。数据构造保证：由于错误分隔符、引号字符或跳过行数导致的错误解析，要么产生畸形输出，要么无法访问正确答案。

#### 任务实例与划分

每个任务实例由文件名 `n`、生成的 CSV 文件以及要求 Agent 从文件计算答案的查询组成。我们共生成 2,000 个任务实例，划分为 1,400 个训练、300 个验证和 300 个测试样本。

### H. 潘多拉魔盒问题的神谕策略

算法 1 给出潘多拉魔盒问题的最优策略；本附录证明其最优性。我们先刻画最优策略的结构。在任意状态，令 `S` 为剩余盒子集合，`q_i(S)` 为盒子 `i∈S` 含奖品的后验概率。最优策略每一步只需考虑后验概率最高的盒子。

第一，如果 Agent 提交，期望奖励等于所选盒子的后验成功概率。因此，选择任何非最大后验盒子都是次优的。

第二，验证只有当它能提高在进一步折扣之前提前终止的概率时才有益。验证后验更高的盒子会提高立即成功的概率，因而弱占优验证后验更低的盒子。因此，每一步只需考虑：

$$
i^\star\in\arg\max_{i\in S}q_i(S)
$$

令 `q=q_i*(S)` 为最可能盒子的后验概率。证明通过值函数递归进行；最优策略在 `q>γ` 时提交最可能盒子，否则验证最可能盒子、更新后验并继续。该递归正是算法 1 的实现，基础情况为 `V({i})=1`。
