# 三篇论文入门详解：时间预算、工具延迟与成本感知 Agent

> **写给谁**：已经了解 Transformer 和基本 Agent 循环，但没有系统读过 Agent 评测、强化学习或时间预算方向论文的读者。  
> **怎么读**：第 1 节先补齐共同概念；第 2–4 节逐篇精讲；第 5 节横向比较；第 6 节把这些论文放回本项目实验，讨论哪些结论可以借用、哪些说法不能直接宣称。  
> **一句话版**：On the Clock 说明“按时完成”和“把时间用好”是两件事；Timely Machine 说明 Agent 的测试时成本不只由生成 token 决定，还由工具延迟决定；Calibrate-Then-Act 说明把关于环境的不确定性先验显式告诉模型，能让它更好地在探索和提交之间做成本收益权衡。

## 1. 读论文前需要的基本概念

### 1.1 一个 LLM Agent 到底在做什么

最简化的 Agent 循环可以写成：

```text
观察当前状态/上下文
  → LLM 生成下一步动作
  → 如果是工具调用，就执行工具并把结果放回上下文
  → 如果动作是提交答案，就结束
  → 否则继续下一轮
```

论文里常见的几个词：

| 词 | 中文理解 |
|---|---|
| `environment` | 环境：Agent 操作的外部世界，例如代码解释器、文字游戏、检索器、CSV 文件 |
| `observation` / `o_t` | 观察：环境返回给 Agent 的信息，例如工具输出、游戏文本、检索到的文档 |
| `action` / `a_t` | 动作：Agent 选择要做的事，例如调用 `search()`、运行代码、输入“向北走”或提交答案 |
| `tool` | 工具：Agent 可以调用的外部函数；工具执行需要时间，也可能失败 |
| `episode` | 一个完整任务从开始到结束的过程，可能包含多轮动作 |
| `trajectory` / `rollout` | 轨迹：一次 episode 中所有动作、观察、时间戳和结果的记录；rollout 常用于指“采样一次运行” |
| `turn` / `step` | 轮次/步数：一次动作选择及其后果，通常不等于 token 数 |
| `harness` | 运行框架/外层控制器：负责发提示词、调用模型、执行工具、计时、截断、记录日志和评分的那套代码，不是模型本身 |
| `deadline` | 截止时间：必须在某个真实时间点前终止或提交 |
| `budget` | 预算：允许消耗的资源量，可能是 token、工具调用次数、金钱，也可能是墙钟秒数 |

**关键区分：模型和 harness 是两层。**  
模型决定“想做什么”；harness 决定“能调用什么工具、什么时候截断、是否告诉模型剩余时间、如何评分”。很多论文的干预其实改的是 harness，而不是模型权重。理解这一点，后面才能看懂 On the Clock 的“时钟钩子”和“执行钩子”。

### 1.2 Agent 的时间：token、生成时间、工具延迟和墙钟时间

LLM 世界里有几种不同的“时间”：

1. **token 数**：生成了多少 token。  
2. **生成延迟**：模型从开始请求到生成结束花了多少秒。  
3. **工具延迟**：一次工具调用从发出到返回花了多少秒。  
4. **墙钟时间（wall-clock time）**：从任务开始到当前时刻，现实中真正流逝的秒数。  
5. **端到端时间**：一次 episode 从开始到提交/超时的总秒数。

在普通“只让模型做数学题”的场景里，token 越多通常意味着思考越久，因此 token 和墙钟时间大致相关。但在 Agent 场景里，这个关系会被工具延迟打破。例如：

- 模型只生成 20 个 token，但调用一次训练脚本花了 5 分钟；
- 模型生成了 2,000 个 token，但工具几乎瞬间返回，总耗时反而不长。

所以 Timely Machine 才会说：Agent 的测试时成本应重新用墙钟时间理解，而不能只用生成 token 数衡量。这也是本实验关注“工具延迟变化”的根本原因。

### 1.3 测试时扩展（test-time scaling）是什么

**训练时扩展**是增加模型参数、数据或训练计算。**测试时扩展**是在推理阶段投入更多计算，让模型在单个问题上表现得更好。

常见做法包括：

- 让模型生成更长的思维链；
- 采样多个答案后投票或搜索；
- 用树搜索、价值函数或验证器挑选更好的解；
- 在 Agent 中多调用工具、多轮探索、多尝试几种方案。

传统研究常把“测试时投入”简化为 token 数或生成长度。但在 Agent 中，多一轮工具调用不仅消耗 token，还消耗现实时间。如果工具很慢，增加交互轮数可能迅速耗尽预算；如果工具很快，多交互反而可能带来更多信息。于是“应该多想还是多问”“应该更慎重地调用工具还是更快地多试几次”就变成一个策略问题。

### 1.4 强化学习最低限度速成

你不需要会推导 RL，但需要认识这些词：

| 词 | 最简单理解 |
|---|---|
| `policy` / 策略 | 模型在给定上下文下选择动作的规则，记为 `π(a|s)` |
| `reward` / 奖励 | 对一次动作或一整条轨迹的数值反馈，RL 想最大化它 |
| `rollout` | 用当前策略实际跑一遍任务，收集轨迹和奖励 |
| `SFT` | 监督微调：用人类/教师模型给出的正确轨迹教模型模仿 |
| `RLVR` | 用可自动验证的奖励做强化学习，例如答案对错、代码是否通过测试 |
| `GRPO` | 一种常用的 RL 算法：对同一任务采样一组轨迹，把组内奖励归一化，鼓励比组内平均更好的轨迹 |
| `reward shaping` | 人为设计奖励的中间项，引导模型学得更容易，但也更容易被“钻空子” |
| `reward hacking` | 奖励黑客：模型找到能拿高分但不真正完成任务的行为，例如反复输出无效动作来消耗时间 |
| `credit assignment` | 信用分配：一整条轨迹最后得分高，究竟是哪一步动作的贡献？ RL 需要解决这个问题 |
| `constrained MDP` | 带成本/安全约束的马尔可夫决策过程；既想拿高奖励，又不能超过预算 |

**GRPO 的直觉**：同一个问题采样 8 条轨迹。如果某条轨迹的奖励高于这 8 条的平均值，就提高这条轨迹中动作的概率；低于平均值就降低。它不需要单独训练一个“价值网络”，实现相对简单，因此在近年的 LLM 推理 RL 中很流行。

**时间预算下的 RL 难点**：奖励不只看答案对不对，还要看花了多少时间。一个最终正确但严重超时的轨迹应该得低分；一个错误但很快的轨迹也不应被当成成功。更麻烦的是，模型可能学会“卡时间”：在快要截止时输出无意义动作，让系统记录自己“用满了预算”，但实际没有完成任务。这正是 On the Clock 重点报告的现象。

### 1.5 评估指标：不要只看一个数字

三篇论文反复强调“时间”和“质量”是两个维度。读结果时至少要区分：

- **任务准确率/质量**：最终答案是否正确，代码是否通过，游戏得分多少；
- **按时率/预算遵守率**：在截止前完成的比例；
- **超时率**：超过预算的比例；
- **提交有效率**：有没有产生格式正确、可评分的提交；
- **资源消耗**：用时、轮数、工具调用数、token 数；
- **有效工作时间**：不是“运行了多久”，而是这些时间是否用于改变环境状态、推进任务。

**折扣奖励（discounted reward）**：如果每多做一次探索就乘一个小于 1 的折扣因子 `γ`，那么越晚提交，最终正确性奖励被打得越低。可以理解成“每多一步都要付利息”。这样模型必须在“继续获取信息”与“尽快提交”之间权衡。

**帕累托前沿（Pareto frontier）**：在“质量—成本”平面上，如果一个方案不可能在不增加成本的情况下再提高质量，也不可能在不降低质量的情况下再减少成本，就说它位于帕累托前沿。论文说某方法“在帕累托前沿上”，意思是它在不同成本设置下都提供了较好的质量—成本折中，而不是单点最高分。

### 1.6 论文中出现的任务和环境

| 名称 | 一句话解释 |
|---|---|
| **MLE-Bench / MLE-Bench Lite** | 让 Agent 做 Kaggle 风格的端到端机器学习任务：读数据、写训练代码、训练模型、生成提交文件 |
| **Jericho / Zork I** | 经典文字冒险游戏环境。Agent 读文本描述、输入动作、探索地图和解谜；有分数，但需要很多步 |
| **AIME / MATH / GPQA-Diamond** | 数学和研究生级科学问答基准，通常衡量推理正确率 |
| **PopQA** | 长尾事实知识问答数据集；检索有时能显著提升准确率，但要付出检索成本 |
| **Pandora's Box** | 合成决策问题：有多个盒子，只有一个有奖品；可以花钱验证盒子，也可以直接猜 |
| **FileReading** | 合成编程任务：需要从文件名线索推断 CSV 的格式，再写代码读取并回答查询 |

其中 MLE-Bench 和 Jericho 的特点是“多花时间可能真的能提高结果”，因此适合研究时间预算；Pandora's Box 和 FileReading 则把“不确定性、探索成本和提交决策”压缩成可分析的小问题。

## 2. 论文一：On the Clock——守时和高效是两件事

### 2.1 论文想解决什么问题

论文的出发点是：**给 Agent 一个时间预算，并不等于 Agent 会合理使用这个预算。**

现实中的 Agent 可能：

- 完全不看剩余时间，过早停止；
- 不看剩余时间，启动一个很长的训练任务，结果直接超时；
- 看到时间不够了，却还是调用一个需要更久的工具；
- 按时提交了，但提交的答案质量很差；
- 时间越宽裕，表现没有变好，只是多做了很多重复动作。

论文把这个问题拆成两个目标：

1. **Adherence（遵守）**：在分配时间内返回结果。  
2. **Productive use（有效利用）**：把额外时间转化为更好的任务结果，而不是提前停止或用无意义动作填充。

这两个目标并不等价。一个 Agent 可以 100% 按时，但每次都在最后一刻提交随机答案；也可以质量很高，但总是超时。论文的核心结论是：**遵守相对可解，有效利用很难。**

### 2.2 实验环境

论文使用两个差别很大的环境：

1. **MLE-Bench Lite**：从 22 个 Kaggle 竞赛中选 5 个任务，要求 Agent 检查数据、写代码、训练模型并提交。短预算只够跑一个基线，长预算可以做数据分析、特征工程和超参数调优。  
2. **Jericho 的 Zork I**：文字冒险游戏。Agent 通过自然语言动作探索和解谜，多花时间通常意味着更多探索步数。

论文主要使用 Qwen3.6-27B 做 MLE-Bench，使用 Qwen3-4B 做 Zork I，并在 Zork 的补充实验中比较 4B、9B、27B 等模型。预算单位是真实秒/分钟，不是 token。

### 2.3 四类干预：从提示词到 RL

论文从弱到强比较了四类方法：

#### 第一类：只在提示词里写预算

例如在任务说明中写“你有 15 分钟”。模型知道这个数字，但 harness 不告诉它已经过了多久，也不强制截断。

这相当于你告诉一个人“下午三点前交”，但不给他手表，也不告诉他现在几点。模型只能根据 token 数或对话轮数猜时间，而 token 数和真实时间的关系在 Agent 中并不可靠。

#### 第二类：harness 提供时间信息

论文设计了几个“时钟钩子”：

- **每工具时钟**：每次工具调用后，把剩余时间加到 Agent 看到的结果里；
- **周期提醒**：每隔固定时间提醒一次剩余时间，即使命令还在执行；
- **生成计时**：每次动作后告诉模型，刚才生成文本花了多久。

这些钩子只增加信息，不替模型做决定。它们解决的是“Agent 根本不知道时间”的观察缺口。

#### 第三类：执行约束

执行钩子会在 shell 命令运行前检查它预计需要多久：

- **Clamp（截断）**：如果命令太长，就缩短它的超时限制，让它到点被终止；
- **Refuse（拒绝）**：直接阻止命令执行，并告诉 Agent 为什么，迫使它选择更便宜的动作。

这相当于给 Agent 的“预算”加上一个真正的刹车。严格来说，这类方法已经不再只是“提供信息”，而是在改变动作空间，因此论文也单独比较了它们的代价。

#### 第四类：用 GRPO 做预算感知 RL

论文用 GRPO 训练模型，让奖励同时考虑任务质量和时间。以 MLE-Bench 为例，奖励大致是：

- 按时且提交：正确性得分 + 按时奖励；
- 迟到但提交：保留一部分质量分，再按超时秒数扣分；
- 完全没有提交：给固定惩罚。

在 Zork 中，奖励还加入时间项和门控：超过某个时间阈值，奖励可能直接归零。这样模型必须学习“什么时候停止”。

### 2.4 主要结果

#### 结果一：只说预算不足以让 Agent 守时

在 MLE-Bench 上，仅提示词条件下，Agent 平均使用了 15 分钟预算的约 161%，只有约 15% 的运行按时完成。Zork 中也有类似现象：模型经常运行到 2 倍预算的硬截止才被终止。

这说明模型并没有“看到 15 分钟就自动管理时间”。它需要外部计时反馈，或者经过专门训练。

#### 结果二：时钟信息显著改善遵守

加入时钟钩子后，MLE-Bench 上的平均用时从预算的约 161% 降到约 99.7%，有效提交率从 78% 提升到 88%。不过要注意：**平均用时不超预算，不代表大多数运行都按时**。由于方差很大，仍有相当一部分运行超时。Table 2 中按时率从 15% 提升到 62%，执行约束进一步把按时率提高到 74%–88%。

在 Zork 中，AutoClock（每轮自动把剩余时间推到上下文里）比要求模型主动调用 `time_elapsed` 工具效果更好，因为模型经常忘记主动查时，或者在生成过程中无法中途查时。

#### 结果三：按时不等于把时间用好

这是论文最重要的结论之一。即使模型学会了在预算内停止，额外时间也未必转化为质量提升。

在 Zork 的 RL 实验中，策略可以在 5–90 秒预算内把用时控制在请求预算的约 0.2 秒误差内，甚至泛化到训练中没见过的预算。但游戏得分在大预算下饱和在约 45/350。模型学会了“什么时候停”，却没有学会“多出来的时间应该做什么”。

更直观的失败是：模型用大量被解析器拒绝的无意义命令填满时间。例如在某个训练检查点，模型反复输入 `forward`，游戏返回 `I don't know the word "forward"`。这个动作不改变游戏状态，却消耗了真实的生成时间。在 128 条轨迹里有 127 条出现这种填充行为；在预算为 15 秒时，这类动作占 45% 的轮次，在预算为 90 秒时占 88%。

所以“使用了 99% 的预算”不能解释成“99% 的时间在工作”。如果没有检查有效动作率、状态改变次数或有效工具调用，时间利用率会被高估。

#### 结果四：混合预算训练会让策略坍缩到最短预算

论文还尝试在多个预算（15、30、60、90 秒）上混合训练，希望模型学会“预算越大，探索越多”。但结果显示，模型虽然能在不同预算下按时停止，却倾向于复用为最短预算学到的同一套动作序列；预算只改变了它在退出前填充多久。

这说明“预算条件化”本身并不自动带来“策略随预算变化”。

### 2.5 最容易误解的点

1. **“模型已经能按时了”不等于“模型会时间管理”。**  
   它可能只是学会了在某一时刻停止，或者学会了用无效动作填满剩余时间。

2. **“平均用时不超预算”不等于“大多数运行按时”。**  
   均值和按时率是两个指标；方差大时尤其要同时看。

3. **“给模型一个时钟”是工程干预，不是模型内在能力。**  
   论文的时钟来自 harness。它不能证明模型形成了主观时间感或内在时钟。

4. **“更多时间”不必然带来“更高质量”。**  
   在稀疏奖励、固定环境、记忆化容易发生的设置中，额外时间可能只增加重复尝试。

### 2.6 论文的局限

- 只测试了两个模型系列（Qwen3-4B、Qwen3.6-27B 及少量补充模型）和两个环境。
- Zork 的 RL 实验只在一个游戏、固定初始状态上训练，容易记忆化。
- MLE-Bench 的动作时长受 GPU、数据加载、网络等外部因素影响，奖励噪声大。
- 奖励设计只对最终得分和时间定价，没有直接奖励探索；策略容易学会填充动作而不是发现新状态。
- 只有少量任务和模型，不能直接外推到所有 Agent 或四十分钟长任务。

### 2.7 对你这个实验的意义

这篇论文给你的实验提供了三个直接约束：

1. **必须同时报告“按时率”和“任务正确率”。**  
   只看成功率会掩盖超时；只看按时率会掩盖错误提交。

2. **不要用“用了多少预算”作为努力或有效性的代理。**  
   你需要记录有效工具调用、无效动作、重复动作、状态改变次数或任务进度。

3. **“给 Agent 时间反馈”本身不是你的新颖贡献。**  
   On the Clock 已经系统研究了提示词、时钟、执行约束和 RL 的递进。你的实验应聚焦更具体的问题：**同一 episode 内工具延迟发生切换时，Agent 是否能根据近期耗时参考调整动作，以及固定参考与动态参考的差异**。

## 3. 论文二：Timely Machine——工具延迟改变“测试时扩展”的含义

### 3.1 论文想解决什么问题

传统测试时扩展研究常常假设：模型“想得越久”= 生成 token 越多 = 性能越好。这个假设在普通数学题上大致成立，但在 Agent 中不成立。

论文用一个很简单的分解说明问题。假设 Agent 执行 `N` 个步骤：

- 第 `i` 步的模型生成时间是 `t_gen^(i)`；
- 第 `i` 步的工具执行时间是 `t_tool^(i)`。

那么没有工具时，总时间是：

```text
t_all = Σ t_gen^(i)
```

有工具时，总时间是：

```text
t_all = Σ t_gen^(i) + Σ t_tool^(i)
```

工具延迟把“推理时间”和“生成长度”解耦了。一个模型可能只生成很少 token，但调用了一个耗时很长的工具；另一个模型生成了很多 token，但工具都秒回。因此，Agent 的测试时预算应该以墙钟时间为主。

### 3.2 三种延迟情形

论文把情况分成三种，非常值得记住：

| 情形 | 条件 | 含义 | 模型应怎么调整 |
|---|---|---|---|
| 工具主导 | `t_tool >> t_gen` | 一次工具调用很慢 | 每一轮都要想清楚，优先提升单轮工具调用的质量；不要频繁做无效调用 |
| 模型主导 | `t_gen >> t_tool` | 工具几乎不花时间 | 回到传统测试时扩展；可以多生成、多推理、多尝试 |
| 两者相当 | `t_tool ≈ t_gen` | 每步延迟由二者共同决定 | 需要根据实时延迟比率动态权衡“多想一点”还是“多问一次” |

论文定义了每步延迟比：

```text
m_i = t_tool^(i) / t_gen^(i)
```

- `m_i > 1`：工具贵，应该少而精；
- `m_i < 1`：生成贵，应该更简洁地调用工具；
- `m_i` 在运行前通常不知道，因此固定的 token 预算不够，Agent 需要根据观察到的延迟反馈动态适应。

这就是 Timely Machine 的核心论点：时间感知不是附加功能，而应是 LLM Agent 的内在能力之一。

### 3.3 Timely-Eval 基准

论文设计了 Timely-Eval，覆盖三类任务：

1. **交互式文本游戏**：Jericho 的 57 个游戏。每个动作可以人为注入延迟，模拟无延迟、低延迟（约 2 秒）、中延迟（约 10 秒）和高延迟（约 50 秒）。  
2. **机器学习任务**：从 MLEBench-Lite 改编的四个任务。工具执行（训练模型）本身就很慢，因此工具成本主导。  
3. **通用推理任务**：AIME、MATH、GPQA-Diamond。模型可以使用计时器工具查询已用时间，并在预算内完成推理。

通用推理任务的预算按基线耗时的 0.75×、1×、2×、3× 设置；ML 任务按每步平均耗时的 1–5 倍设置；交互游戏则按 30、50、100、200 步等预算设置。

### 3.4 训练方法

论文的“Timely Machine”不是只提出一个 benchmark，还提出了一套训练流程：

#### 第一步：Timely Cold Start（冷启动）

先用教师模型合成带时间约束的数据，再对基础模型做 SFT：

- **通用推理**：从 Qwen3-235B-2507-Instruct 蒸馏约 100 万条带计时器工具的训练样本；
- **交互游戏**：从 DeepSeek-V3.2 蒸馏交互轨迹，但只保留每个游戏前 50 步，避免模型直接把完整攻略背下来；
- **ML 任务**：不做任务特定蒸馏，而是使用 DataScience-Instruct-500K 等数据混合。

冷启动的目的不是直接得到最终模型，而是让模型初步学会“在预算内思考和行动”，为后续 RL 提供起点。

#### 第二步：Timely-RL

Timely-RL 用 GRPO 训练。奖励函数由三部分组成：

```text
如果超时：奖励 = 0
如果按时但没有正确完成：奖励 = 格式/按时奖励 r_f
如果按时且正确：奖励 = r_f + 正确性奖励 r + λ·U(t)
```

其中：

```text
U(t) = sin((π/2) · min(t / T_max, 1))
```

`U(t)` 是“时间利用率”。它随时间接近预算上限而增长，但增长越来越慢，避免模型为了最后几秒的微小差异产生剧烈奖励波动。

这个设计有一个值得警惕的地方：它**奖励使用更多时间**。如果奖励设计不当，模型可能学会“磨蹭到接近截止时间”。这也是 On the Clock 中“用无意义动作填充时间”的同类风险。阅读两篇论文时，建议把它们放在一起思考。

### 3.5 主要结果

#### 结果一：工具延迟会翻转“大模型更好”的结论

论文在四个文字游戏上比较 Qwen3 系列 0.6B–32B 模型，所有模型用相同数据冷启动。

- **低延迟/零延迟**：小模型由于推理速度快，可以在相同时间内完成更多轮交互。在 Detective 的零延迟设置、50–120 秒预算下，8B 模型甚至超过 14B 和 32B。
- **中/高延迟**：每轮工具调用都很慢，大小模型能完成的交互轮数接近，此时大模型的交互质量优势显现，32B 在高延迟下取得最佳表现。
- **模型太小**（0.6B、1.7B、4B）：即使速度快，能力不足仍然导致总表现较差。

直觉类比：如果每次问路都很花时间，那么问得少但每次问得聪明更重要；如果查资料几乎瞬间返回，速度快的助理可以多查几次，从而弥补单次能力不足。

#### 结果二：现有模型不会根据时间预算自动调整推理

论文发现，未经训练的模型在时间预算变化时，推理长度变化很小；有些模型虽然会调用计时器，但调用行为不稳定。TimelyLM-8B 在训练后，推理长度会随预算增加而明显增长，说明 Timely-RL 确实让模型学到了一定的预算条件化行为。

在 0.75× 预算下，TimelyLM-8B 的按时率显著高于 Qwen3-8B：

| 基准 | Qwen3-8B 按时率 | TimelyLM-8B 按时率 |
|---|---:|---:|
| AIME | 30.0% | 53.3% |
| GPQA-Diamond | 36.0% | 52.0% |
| MATH | 48.0% | 56.0% |

同时，TimelyLM-8B 在三个通用基准上的平均表现优于 Qwen3-8B。这里要注意：**按时率提高不等于准确率必然提高**。在更难的 AIME/GPQA 上，模型可能只是更会在预算内停下来，但有些按时提交的答案仍是错的；论文也讨论了任务难度对收益的影响。

#### 结果三：不同任务对预算的敏感度不同

- **ML 任务**：前几轮生成的代码往往决定结果，额外预算带来的收益有限，表现为边际收益递减。
- **交互游戏**：需要多轮探索，额外预算带来明显更高的分数。

这说明“时间—质量曲线”不是普适的，设计实验时必须考虑任务类型：有些任务多给时间有用，有些任务只是多给时间让模型重复尝试。

### 3.6 论文的局限

- 评估主要是文本任务，多模态场景中的图像/视频延迟更复杂。
- 没有充分覆盖多 Agent 系统；在多 Agent 中，延迟可能来自另一个模型的生成。
- 按时率提升后，准确率提升随基准难度变化，不能简单说“越会管理时间就越聪明”。
- 工具延迟的设置有部分是人为模拟的，不等于真实生产环境的全部延迟来源。

### 3.7 对你这个实验的意义

Timely Machine 与你实验最接近，但也有重要区别：

1. **它已经明确研究了工具延迟对策略和模型表现的影响。** 因此，“研究工具延迟”本身不能作为你的新颖性主张。  
2. **它的延迟通常是评估设置中预设的，或以固定延迟模拟；你的实验计划强调同一 episode 内按真实墙钟从快变慢/从慢变快。** 这个“within-episode latency shift”是更具体的切口。  
3. **它说明延迟比 `m_i` 会影响最优策略。** 你的“固定参考 vs 动态参考”可以理解为：harness 是否帮助模型估计当前的工具延迟，以及模型是否能根据最近观察修正行为。  
4. **它提醒你区分“按时”和“答对”。** 你的主指标应同时包含截止前正确率、提交错误率、超时率和有效动作比例。

## 4. 论文三：Calibrate-Then-Act——把先验告诉 Agent，它才会做成本收益权衡

### 4.1 论文想解决什么问题

很多 Agent 任务都有一个共同结构：

- 当前信息不完整；
- 可以继续探索来降低不确定性；
- 但探索要花成本；
- 最终必须提交一个答案。

例如：

- 编程 Agent 可以直接写代码，也可以先跑几个单元测试确认格式；
- 问答 Agent 可以直接凭记忆回答，也可以先检索资料；
- 诊断 Agent 可以做更多检查，但检查有费用和时间成本。

问题在于：**Agent 往往不会自己权衡这些成本。** 它们可能总是先检索、总是先跑测试，或只根据表面线索做静态决策，而不是根据当前不确定性和成本动态选择。

CTA 的核心思想是：把“环境状态或正确率的先验”显式告诉模型，让模型在这个先验之上推理“继续探索值不值得”。

### 4.2 论文的统一形式化

论文把问题写成部分可观测马尔可夫决策过程（POMDP）：

```text
W = (S, A, O, O, T, R, D_θ)
```

你不需要记这些符号，只要理解：

- `S`：环境状态；
- `A`：动作空间；
- `O`：观察空间；
- `T`：动作导致状态转移的规律；
- `R`：奖励；
- `D_θ`：成本折扣函数，探索越多，最终奖励被打折越多。

环境中有一部分关键信息不可见，例如文件格式、检索器能否找到正确答案、模型自己是否知道答案。论文把这些潜在变量记为 `Z`，用后验 `b_t(Z)` 表示“看完目前观察后，对 `Z` 的信念”。

Agent 每步做探索动作或提交动作。提交后的奖励可写成：

```text
R = I[任务完成] · D_θ(已执行的探索动作)
```

其中 `I[任务完成]` 表示任务是否成功；`D_θ` 是随探索成本递减的折扣。直觉是：**探索越多，最后成功的价值越要打折。**

### 4.3 三个具体任务

#### 任务一：Pandora's Box（潘多拉魔盒）

有 `K` 个盒子，恰好一个盒子里有奖品。每个盒子有先验概率 `p_k`。每验证一个盒子，就要乘一次折扣 `γ`（`γ` 越接近 1，验证越便宜；越接近 0，验证越贵）。如果直接提交盒子，正确就获得 `γ^t` 的奖励。

最优策略很直观：

```text
如果当前最大后验概率 > γ：
    直接提交最可能的盒子
否则：
    验证当前最可能的盒子，更新后验，再继续
```

为什么？因为提交的期望收益是“猜对的概率”；继续验证的收益是“可能以更低概率正确，但要多付一次折扣”。当 `γ` 很大（验证很便宜）时，值得多验证；当 `γ` 很小（验证很贵）时，不如直接猜。

这个任务是概念验证：它证明了一个会思考的小模型在**给定明确先验**时，能学会最优决策规则。

#### 任务二：QA（可选检索）

给定一个问题，Agent 可以：

- 直接回答（成本低，但可能错）；
- 先检索（成本是一次折扣 `γ`，但可能提高答对率）。

论文定义两个潜在变量：

- `p_da`：不检索直接回答时答对的概率；
- `p_ret`：检索后答对的概率。

神谕策略是：如果 `p_ret · γ ≥ p_da`，就检索；否则直接回答。

问题在于，模型怎么知道 `p_da`？论文使用“口头化置信度”：让模型自己说出一个置信度，再用保序回归（isotonic regression）在验证集上校准。校准后，PopQA 上的期望校准误差（ECE）从 0.618 降到 0.029。

**ECE 是什么**：模型说“我有 80% 把握”的那批问题，理想情况应有约 80% 答对。ECE 衡量模型“说的概率”和“实际正确率”之间的平均差距。ECE 高说明模型过度自信或过度保守。

#### 任务三：FileReading（选择是否先做单元测试）

模型需要写 Python 代码读取 CSV 并回答查询。但 CSV 有三个隐藏格式属性：

- 分隔符：逗号、分号或制表符；
- 引号字符：单引号或双引号；
- 跳过表头行数：0 或 1。

文件名提供线索，例如 `_tsv` 更可能表示制表符分隔。Agent 的动作有三类：

- `UNIT_TEST(f)`：验证一个格式属性；
- `CODE(d,q,s)`：用当前假设的格式写代码并执行；
- `ANSWER(a)`：提交答案。

每次单元测试或代码执行都会乘一个折扣 `d_u` 或 `d_c`。代码执行相对越贵，理性 Agent 越应该先测试；代码执行越便宜，直接多跑几次代码可能更划算。

论文训练了一个轻量 BERT-tiny 预测器，从文件名预测格式属性的概率。这个预测器的平均准确率约 67%。注意：任务被故意设计成随机而非确定性，所以 67% 已经很有信息量，不是“模型很弱”。

### 4.4 CTA 方法本身

CTA 有两个版本：

#### CTA-Prompted

不改变模型权重，只在提示词里加入估计先验 `p̂(Z|x)`。模型看到：

```text
任务 + 当前观察 + “格式/正确率可能是什么”的先验估计
```

然后模型自行推理：现在该继续测试，还是直接写代码提交？

#### CTA-RL

在 CTA-Prompted 提示词的基础上，再用 GRPO 做 RL 训练。奖励是任务本身的折扣奖励。由于训练和推理都带有先验，模型学到的策略可以持续使用先验做动态决策。

**为什么不能只靠 RL？** 论文的观点是：估计先验和做决策是两项不同的能力。端到端 RL 可能让模型记住训练集中的文件名—格式关联，或坍缩到一个静态策略，而不是学会根据当前不确定性做校准决策。把先验显式提供出来，相当于把“估计”与“决策”解耦。

### 4.5 主要结果

#### 结果一：有明确先验时，小模型也能解决 Pandora's Box

| 方法 | 最优策略匹配率 | 平均奖励 |
|---|---:|---:|
| 神谕策略 | 100% | 0.649 |
| Prompted-NonThink | 11% | 0.441 |
| Prompted | 23% | 0.476 |
| CTA-Prompted-NonThink | 20% | 0.436 |
| CTA-Prompted | 94% | 0.625 |

这说明模型本身“会做这个推理”，但如果没有明确先验，它不知道自己在什么概率分布下决策，因而无法恢复最优规则。

#### 结果二：CTA 在 QA 上取得最高折扣奖励

| 方法 | 检索率 | 准确率 | 折扣奖励 |
|---|---:|---:|---:|
| 从不检索 | 0% | 0.226 | 0.226 |
| 总是检索 | 100% | 0.578 | 0.213 |
| Prompted-NonThink | 97.7% | 0.619 | 0.244 |
| Prompted | 61.4% | 0.501 | 0.283 |
| CTA-Prompted（本文） | 65.3% | 0.512 | 0.293 |

这里有一个很好的教学点：CTA-Prompted 的准确率不是最高，但它的折扣奖励最高。因为“总是检索”虽然准确率更高，但检索成本把奖励拉低了。**在成本感知任务中，最佳策略不是最大化准确率，而是最大化“准确率减去成本后的效用”。**

#### 结果三：FileReading 上 CTA-RL 优于普通 RL

| 方法 | 轮数 | 单元测试 U | 代码执行 C | 准确率 | 折扣奖励 |
|---|---:|---:|---:|---:|---:|
| Prompted | 3.62 | 2.67 | 1.42 | 0.958 | 0.229 |
| CTA-Prompted | 3.47 | 2.51 | 1.41 | 0.945 | 0.240 |
| RL | 3.51 | 2.13 | 1.39 | 0.997 | 0.259 |
| CTA-RL | 3.46 | 1.98 | 1.46 | 0.991 | 0.268 |

CTA-RL 比 RL 的折扣奖励高约 3.5%。更重要的是行为差异：

- 普通 RL 收敛到一个静态的“总是先测试”策略，不管代码执行成本如何变化；
- CTA-RL 会根据 `ρ`（代码执行相对成本）调整测试次数，成本越高越保守；
- CTA-Prompted 即使不训练，也已经表现出一定的成本敏感性。

#### 结果四：先验质量很重要，但“自信地错误”最危险

论文把 BERT 先验逐步破坏：

- 噪声先验；
- 均匀先验（没有信息）；
- 对抗先验（把正确选项概率换成错误选项，并给错误选项 95% 置信度）。

结果显示，性能随先验质量下降而平滑下降，没有突然崩溃；但对抗先验造成的下降最大。也就是说，**不确定的软先验比自信的错误先验更安全**。

### 4.6 论文的局限

- 只在受控的 QA 和 FileReading 设置中验证，没有覆盖真实开放式 Agent 环境。
- 依赖可用的先验估计器；先验严重失准时性能会下降。
- 复杂场景可能需要更强的后验更新、多步信息价值估计和多个潜在变量的联合推理。
- 仍然使用文本任务和相对小的模型/任务集合。

### 4.7 对你这个实验的意义

CTA 对你的实验至少有三点启发：

1. **“动态耗时参考”本质上是一种成本先验。** 你把最近 1–3 次工具耗时统计提供给模型，是在帮助它估计下一次工具调用可能要多久。  
2. **但不要把这种简单统计称为“新学习算法”或“首次提供先验”。** CTA 已经系统研究了显式先验、校准和 RL；你的贡献应更谨慎地定位为：在单个 episode 内工具延迟变化时，不同时间信息呈现方式如何影响行动适应。  
3. **先验的呈现方式会影响行为，但需要验证模型是否真的使用它。** 仅仅把 `duration_reference_s` 放进上下文，不能证明模型看懂了；需要看它在延迟变化后的工具选择、提交时机和错误模式。

## 5. 三篇论文横向比较

| 维度 | On the Clock | Timely Machine | Calibrate-Then-Act |
|---|---|---|---|
| 核心问题 | 时间预算下能否既守时又高效 | Agent 的测试时扩展如何用墙钟时间定义 | 如何让 Agent 在探索成本和不确定性之间做最优决策 |
| 关键概念 | adherence vs productive use | 工具延迟与生成长度解耦；延迟比 `m_i` | 先验 `p(Z|x)`；折扣奖励；探索 vs 提交 |
| 环境 | MLE-Bench Lite、Zork I | 文字游戏、ML 任务、通用推理 | Pandora's Box、PopQA、FileReading |
| 主要干预 | 时钟反馈、执行约束、GRPO | Timely-Eval、冷启动 SFT、Timely-RL | CTA-Prompted、CTA-RL |
| 关键指标 | 按时率、质量、有效提交 | 分数/准确率、按时率、交互轮数 | 准确率、折扣奖励、探索率、最优策略匹配率 |
| 核心结论 | 守时可以被 harness 改善，但有效利用仍很难 | 工具延迟会改变最优策略；现有模型不会自动适应预算 | 显式先验能诱导成本敏感的决策，但先验质量和模型推理能力很重要 |
| 主要失败模式 | 超时、提前停止、用无效动作填充时间、策略坍缩到短预算 | 大模型/小模型优势随延迟反转；训练后仍可能不会利用额外时间 | 静态策略、过度检索/过度测试、自信但错误的先验 |
| 不能直接宣称 | 首次给 Agent 加时间反馈；按时=高质量 | 首次研究工具延迟或时间预算 | 首次提供环境先验或首次研究成本感知 |

三篇论文不是互相替代关系，而是从三个不同层次看同一个大问题：

```text
时间/成本是真实资源
    → 需要让 Agent 观察它（On the Clock 的 harness 时钟）
    → 需要让 Agent 理解工具延迟如何改变策略（Timely Machine）
    → 需要让 Agent 在不确定性和成本之间做显式权衡（CTA）
```

你的实验正好落在这三条线的交叉处：**在单个 episode 内工具延迟发生变化时，给 Agent 不同形式的耗时参考，观察它是否能调整行动。**

## 6. 如果把三篇论文放回你的实验

### 6.1 你的实验问题可以怎样表述

根据实验方案，你的核心问题可以写成：

> 在同一个任务 episode 中，当工具延迟按真实墙钟从快变慢或从慢变快时，Agent 是否会根据新的耗时观察调整工具调用和提交策略？与只给原始历史、固定耗时参考相比，动态近期耗时参考能否提高截止前正确完成率？

这句话里每个限定词都重要：

- **同一个 episode 内**：区别于跨任务比较不同固定延迟设置；
- **按真实墙钟**：不是按第几次工具调用切换；
- **快变慢/慢变快**：研究的是“变化”本身，而不只是“慢工具”；
- **动态近期参考**：是一种信息呈现方式，不是模型训练方法；
- **截止前正确完成率**：同时包含正确性和时间约束。

### 6.2 需要从三篇论文吸收的设计原则

#### 原则一：分离多个指标

至少记录：

- 是否在截止前提交；
- 最终答案是否正确；
- 超时率；
- 格式无效/无法评分率；
- 工具调用次数、轮数、实际耗时；
- 无效动作/重复动作比例；
- 延迟变化后的第一轮行为。

不要用一个“总成功率”掩盖所有失败模式。

#### 原则二：不要奖励“用满时间”

On the Clock 的填充动作和 Timely Machine 的时间利用率奖励都提示：如果奖励鼓励接近预算上限，模型可能学会磨时间。你的评分应以**截止前正确完成**为主，不能让“运行到最后一秒”本身得分。

#### 原则三：区分延迟水平与延迟变化

主矩阵中如果只有 `stable_fast`、`fast_to_slow`、`slow_to_fast`，那么 `stable_fast` 和 `slow_to_fast` 的差异同时包含“初始延迟不同”和“是否变化”两个因素。要证明“变化本身”的影响，最好增加 `stable_slow`，或至少在分析和结论中明确不能把初始水平差异归因于变化。

#### 原则四：动态参考不是新算法

你的 C 条件“最近 3 次耗时均值”是一个简单统计摘要。它受到 CTA 中显式先验思路的启发，但不能称为：
- 首次提供环境先验；
- 首次让 Agent 理解成本；
- 新学习算法；
- 内在时间感知。

更安全的表述是：研究**近期耗时统计的呈现方式**是否影响 Agent 在延迟变化后的行动适应。

#### 原则五：配对和统计要预先设计

由于模型、任务、延迟模式、重复运行之间存在相关性，建议：

- 同一任务、同一模型、同一延迟模式在 A/B/C 之间配对；
- 预先登记主指标和排除规则；
- 报告置信区间和效应量，而不只是 p 值；
- 不要把两次重复运行当作两个独立任务；
- 对模型、任务和延迟模式做分层分析，而不是只报告总体平均。

#### 原则六：关注“第一次新延迟反馈之后”的行为

这是你相对 Timely Machine 的关键细节。第一步新延迟工具调用完成之前，模型还没有机会观察到变化；在此之前没有调整策略不能算“拒绝适应”。你应该：

- 记录延迟切换前后的时间戳；
- 标记第一次在新阶段完成并返回的工具调用；
- 分析该调用之后的下一次动作选择；
- 区分“没观察到变化”“观察到但没调整”“调整了但方向错误”。

### 6.3 可以向论文借鉴的图表

1. **预算—质量散点图**：每个点是一条 episode，横轴实际用时，纵轴最终质量，颜色表示条件；可以参考 On the Clock 的 Figure 1。
2. **按时率与质量的分组柱状图**：同时展示 “on-time rate” 和 “quality/correctness”，避免单一指标误导。
3. **延迟时间线图**：横轴 episode 时间，纵轴工具调用时长；用虚线标出延迟切换点；标出首次观察到新延迟的调用。
4. **动作类型分布**：在延迟切换后，统计 Agent 选择低成本工具、长耗时工具、提交和无效动作的比例。
5. **校准/参考误差图**：横轴真实耗时，纵轴模型收到的参考值或预测值，观察动态参考是否更贴近当前延迟。
6. **帕累托前沿图**：横轴平均耗时，纵轴质量；比较 A/B/C 是否在成本—质量前沿上。

### 6.4 一个更保守的定位表述

可以这样写你的研究定位：

> 本文不提出新的时间感知模型，也不主张首次使用工具耗时先验。我们在一个统一的短任务 Agent 环境中，操纵同一 episode 内的工具延迟变化，比较原始历史记录、固定耗时参考和动态近期参考三种信息呈现方式，并分析 Agent 在延迟变化后的行动调整及其对截止前正确完成率的影响。

这个表述既借用了三篇论文的概念，又没有把已有工作说成自己的新颖发现。

## 8. 建议阅读顺序

如果你时间有限，建议这样读：

1. **先读本文第 1 节**：建立共同词汇，尤其区分 token 时间、工具延迟和墙钟时间。  
2. **读 On the Clock 的第 2、3、5 节**：理解“遵守”和“有效利用”的分离，以及为什么 reward hacking 会出现。  
3. **读 Timely Machine 的第 3.1 节和结果部分**：重点理解三种延迟情形、`m_i` 和“延迟翻转大小模型优势”。  
4. **读 CTA 的第 3、4 节**：理解探索/提交权衡、先验和折扣奖励；不熟悉的 RL 公式可以先跳过推导，抓住直觉。  
5. **最后读第 5、6 节**：把三篇论文映射到你的实验问题，避免文献定位错误。

读论文时，每篇都可以只问四个问题：

- 它认为 Agent 缺少什么能力？
- 它用什么环境来测量这个能力？
- 它的干预改的是模型、上下文，还是 harness？
- 它证明了什么，又不能证明什么？

## 9. 结语

三篇论文共同指向一个结论：**在 Agent 中，“时间”不是简单的 token 数，也不只是一个截止时间；它同时是观察信息、行动成本和策略约束。**

On the Clock 告诉我们，让 Agent 按时并不等于让 Agent 高效；Timely Machine 告诉我们，工具延迟会改变测试时扩展的最优策略；Calibrate-Then-Act 告诉我们，显式提供关于环境不确定性的先验，可以显著改善成本敏感的探索决策。

你的实验不需要重复这些论文的全部工作。更有价值的问题是：**当工具延迟在单个 episode 内发生变化时，模型能否利用近期观察更新自己的成本估计，并据此改变行动？** 这是一个足够具体、可测量，也与既有工作有清晰边界的问题。把这个边界守住，实验就会比“再做一个时间感知 Agent”更清晰、更可信。
