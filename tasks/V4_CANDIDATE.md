# v4 开发候选：减少证据检索的机械开销

依据 v3 的 18 条开发诊断，变化反馈后继续决策的机会为 12/12，但证据任务 1/9 正确、8/9 超时；仅一题、单次重复，不能据此评估方法效果或外推到其他题型。此前 120 秒预算、统一 30% 变化点和三种环境先保持不变，以可行性为目标，不根据 A/B/C 胜负选择方案。

v4 与 v3 的题面、文档全文、表格、事实、标准答案和评分完全相同。表格仍使用每页 2 行的 v3 查询。证据 `search` 改为仅搜索不含答案的摘要，最多返回 5 条；查询“档案”可获取所有文档 ID 与摘要，随后模型仍须调用 `read_document` 读取事实。预期对三个已知实体的题，模型可以通过一次搜索和三次读取代替三次搜索和三次读取；链式题仍需要读取各条关系后推导。该动作路径是可能而非强制，模型可以自由使用更少或更多调用，也可以提前提交。

搜索只匹配摘要，避免通过猜测全文中的数值来查询是否存在某个答案。摘要披露全部文档名和 ID，但不披露具体数值或链条关系；应继续核查摘要是否间接泄露答案。该调整改变了信息组织和显著性，也改变了允许的工具策略，不能把 v3/v4 之间结果差异归因于单一耗时因素。表格分页仍可能增加机械步骤。

建议使用 `tasks.data_v4.generate`、`call_tool` 和 `tool_schemas`，先以开发集做覆盖不同题型、两族三模式和 A/B/C 的平衡可行性预跑：记录截止前正确、超时、观察变化后仍有决策、无效格式和服务异常；不给提前完成负面奖励，不根据组间胜负改参数。若单题结果不足以排查地板/天花板，应扩展到全部 8 道开发题。开发配置冻结前不得使用测试集效果选择参数。

离线校验：`python -m unittest tests.test_tasks_v4 -v`；未进行 v4 真实模型预跑。正式测试仍需要独立隔离、可靠计时和错误分类、评分与人工复核，不可将候选直接当作冻结方案。
