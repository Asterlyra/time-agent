# v3 开发候选：分页和较早变化点

这不是冻结的正式数据或正式结果。v3 使用与 v2 完全相同的题目、行、标准答案及评分器；仅将表格 `lookup_rows` 改为每次最多 2 行，返回 `next_cursor`。后续页面使用同一表和过滤条件并传入 `cursor`；`next_cursor: null` 表示没有更多数据。输出序列按既有顺序稳定，原始行和答案不被更改。`tool_schemas()` 返回包含新分页说明的独立工具描述；必须使用 `tasks.data_v3.call_tool` 执行，不能与 v2 的 schema 混用。

开发集已完成的 v2 预跑显示：48 条变化模式中 21 条在收到新阶段工具结果后仍有决策；表格 0/24。v2 中两次调用可以取得所有表格行，常在 60 秒变化点前结束。v3 分页预期给表格任务更多观察机会；对典型筛选方式，两张表各有 4 条匹配行，各需两页。仍可以选择其他合法查询策略或提前提交，分页不能保证观察到变化。

建议为下一次开发预跑固定统一的 `shift_fraction=0.30`（预算 120 秒时为 36 秒），两类任务、三种延迟模式及 A/B/C 均使用同一值，其他参数保持现有默认。这个候选依据的是变化是否暴露，而不是按 C/B 效果挑选。先在每类 1 题、三模式及三条件做平衡的 18 条可行性预跑，再根据覆盖、正确性、超时和服务情况决定是否在完整开发集复测；不要将这 18 条当正式效果证据。任何修改应版本化，原 72 条与 v3 不混合；测试集不用于参数选择。

限制：分页增加了机械步骤，可能把性能变化变成对操作次数与格式能力的测量；现有表格模板仍共享相似的筛选连接结构。另一条可选路径是保留 v2 工具不分页，仅统一提前变化点，或设计具有真实信息依赖的分阶段业务任务；实际可用性应事先以开发集验证，不根据哪个条件获胜来选。下一步还需独立核对分页可用性、各条件共享工具结果、评分、变化观察比例、不同任务族的地板/天花板效应，以及 CLI 的隔离和计时问题。

校验：`python -m unittest tests.test_tasks_v3 -v`。尚无 v3 真实预跑、人工复核或正式冻结。
